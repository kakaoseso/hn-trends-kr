15년 넘게 현업에서 엔지니어링을 하다 보면, C++에 대한 일종의 '괴담'을 끊임없이 듣게 된다. Segmentation fault, 메모리 누수, 그리고 수많은 Footgun들. 하지만 C++20과 C++23을 거치며 모던 C++은 우리가 알던 과거의 그 무시무시한 언어에서 꽤 우아하고 강력한 도구로 진화했다.

최근 Hacker News에서 흥미로운 프로젝트를 하나 발견했다. C++ 경험이 전무한 개발자가 8개월 만에 만든 **GOLDE** 라는 Conway's Game of Life 시뮬레이터다. 단순히 화면에 점을 찍는 수준이 아니라, Bill Gosper의 전설적인 **HashLife** 알고리즘을 구현해 수조 세대를 단숨에 시뮬레이션한다.



이 프로젝트의 코드를 뜯어보며, 모던 C++이 어떻게 복잡한 알고리즘을 안전하고 빠르게 담아내는지, 그리고 주니어 개발자가 흔히 빠지는 동시성(Concurrency) 설계의 함정은 무엇인지 짚어보고자 한다.

## HashLife와 메모리 관리의 정석

HashLife의 핵심은 우주를 Memoization이 적용된 Quadtree로 표현하는 것이다. 동일한 패턴은 두 번 다시 계산하지 않는다. $2^n \times 2^n$ 크기의 노드는 $2^{n-2}$ 세대 이후의 미래를 캐싱한다. 즉, 공간을 넓게 볼수록 시간도 기하급수적으로 건너뛸 수 있다.

여기서 가장 눈에 띄는 것은 노드를 메모리에 올리는 방식이다. C++ 초보자들이 흔히 하는 실수는 모든 것을 `std::shared_ptr`로 감싸는 것인데, GOLDE의 작성자는 놀랍게도 **Bump-pointer allocator (Arena Allocator)** 패턴을 선택했다.

```cpp
class LifeNodeArena {
public:
    const LifeNode* emplace(const LifeNode* nw, const LifeNode* ne, const LifeNode* sw, const LifeNode* se);
private:
    constexpr static auto BlockCapacity = 65536UZ / sizeof(LifeNode);
    std::vector<std::unique_ptr<LifeNode, BlockDeleter>> m_Blocks;
    size_t m_Current = BlockCapacity;
};
```

이 구조는 대량의 노드를 연속된 메모리 블록에 할당하여 Cache locality를 극대화한다. 노드 생성 시에는 `placement new` 대신 C++20의 `std::construct_at`을 사용하여 훨씬 안전하고 모던한 방식으로 객체를 초기화한다. 트리 전체가 불변(Immutable)이고 Canonical하기 때문에, 복잡한 스마트 포인터 대신 `const LifeNode*`라는 Raw pointer를 사용하는 것이 성능상 압도적으로 유리하다. 아주 훌륭한 엔지니어링 결정이다.

## Base Case: 비트 연산과 Zero-branching

HashLife가 거대한 트리를 내려가다 보면 결국 가장 작은 단위인 Base case에 도달한다. GOLDE는 8x8 그리드를 Base case로 삼고, 중심부의 4x4 그리드가 2세대 후에 어떻게 변할지 계산한다.

4x4 그리드는 16개의 셀을 가지므로, 정확히 `uint16_t` 하나에 들어맞는다. 경우의 수는 $2^{16} = 65,536$개. 작성자는 이 6만여 개의 패턴을 시작 시점에 미리 계산해 Lookup table로 만들었다.

```cpp
uint16_t WindowCenter(uint16_t nw, uint16_t ne, uint16_t sw, uint16_t se) {
    return ((nw << 10) & MaskNW) | ((ne << 6) & MaskNE) | ((sw >> 6) & MaskSW) | ((se >> 10) & MaskSE);
}
```

이 코드를 보라. 분기문(Branching)이 단 하나도 없다. 오직 비트 시프트와 마스킹 연산만으로 9개의 겹치는 4x4 윈도우를 추출하고, 배열에서 값을 꺼내 조합한다. 현대 CPU 파이프라인에서 Branch prediction 실패로 인한 페널티를 완벽하게 회피하는 교과서적인 최적화다.

## 임의의 세대 점프: Golly vs GOLDE

개인적으로 가장 흥미로웠던 부분은 '정확히 N세대'를 점프하는 로직이다. HashLife는 태생적으로 2의 거듭제곱 단위로만 시간을 건너뛴다. 사용자가 "1000세대만 진행해줘"라고 입력하면 난감해진다.

유명한 시뮬레이터인 Golly의 개발자 Tomas Rokicki는 N을 나눌 수 있는 가장 큰 2의 거듭제곱을 찾아 고정된 스텝으로 반복하는 방식을 썼다. (1000의 경우 8세대씩 125번 점프). 반면 GOLDE는 N보다 작거나 같은 가장 큰 2의 거듭제곱을 빼나가는 탐욕(Greedy) 알고리즘을 사용했다. (512 + 256 + 128 + 64 + 32 + 8).

- **Golly의 방식:** 캐시 히트율이 높다. 동일한 스텝 사이즈를 반복하므로 캐시가 뜨겁게 유지된다.
- **GOLDE의 방식:** 최대 $\log_2{n}$ 번의 점프만으로 목표에 도달한다.

UI의 반응성을 고려한다면 GOLDE의 방식이 직관적이지만, 스텝 사이즈가 매번 달라져 Hash table을 노드 크기와 세대 수 모두로 키(Key)를 잡아야 하는 오버헤드가 발생한다. 프로덕션 환경이라면 Golly의 방식이 Throughput 면에서 더 안정적일 것이다.

## C++ 동시성 설계의 함정과 HN의 비판

UI 반응성을 위해 C++20의 `std::jthread`와 `std::stop_token`을 활용해 무거운 연산을 언제든 우아하게 중단(Graceful shutdown)할 수 있게 만든 점은 칭찬할 만하다. 하지만 캐시의 Thread safety를 다루는 부분에서는 심각한 결함이 보인다.

작성자는 여러 스레드가 동시에 실행될 때의 성능 저하를 막기 위해 `static std::array<HashLifeCache, 256>`를 선언하고, 각 스레드에 `thread_local size_t CacheIndex`를 부여하는 방식을 택했다.

Hacker News의 한 유저(anon)가 정확히 이 부분을 찌르며 비판했다. "이 방식은 CacheIndex가 어떤 캐시를 쓸지 결정할 뿐, HashLifeCache 자체에 대한 동시 접근을 막아주지 않는다. 데이터 레이스가 발생하지 않을 거란 가정은 위험하다."

나 역시 이 의견에 전적으로 동의한다. "시뮬레이션이 일시 정지 상태일 때만 편집이 가능하므로 안전하다"는 작성자의 변명은 전형적인 '내 PC에서는 잘 돌아가요' 식의 위험한 발상이다. Principal Engineer로서 이런 PR을 리뷰했다면 절대 통과시키지 않았을 것이다. 이런 암묵적인 타이밍 가정은 코드가 리팩토링되거나 새로운 기능(예: 백그라운드 자동 저장)이 추가되는 순간 끔찍한 Heisenbug로 돌변한다. 차라리 Sharded Mutex를 사용해 락 경합을 줄이거나, 진정한 의미의 Thread-local 캐시를 운용하고 주기적으로 글로벌 캐시와 병합하는 구조를 택했어야 한다.

## 총평

동시성 설계에서 약간의 헛발질이 있었지만, GOLDE는 전반적으로 매우 훌륭한 C++ 프로젝트다. C++에 입문한 지 8개월 된 개발자가 Arena allocator, Bitwise optimization, C++20/23의 최신 기능들을 이 정도로 조화롭게 엮어냈다는 사실이 놀랍다.

C++은 여전히 날카로운 칼이다. 잘못 휘두르면 손가락이 날아가지만, 규칙을 이해하고 모던 C++의 도구들을 적절히 활용한다면 이보다 더 정교하고 빠른 조각칼은 없다. 무한을 시뮬레이션하고 싶다면, C++은 여전히 최고의 선택지 중 하나다.
