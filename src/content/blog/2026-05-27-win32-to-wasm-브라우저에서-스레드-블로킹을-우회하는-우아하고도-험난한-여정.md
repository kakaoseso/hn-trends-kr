최근 WASM(WebAssembly)이 웹의 미래라는 찬사를 자주 듣습니다. 하지만 실제로 프로덕션 레벨에서 브라우저 내 멀티스레딩이나 블로킹 I/O를 다뤄본 엔지니어라면, 그 이면에 얼마나 끔찍한 제약들이 숨어있는지 잘 아실 겁니다.

오늘 다뤄볼 주제는 Evan Martin의 [Theseus: translating win32 to wasm] 프로젝트입니다. Win32/x86 에뮬레이터인 Theseus를 WASM으로 컴파일해 브라우저 위에서 지뢰찾기 같은 고전 윈도우 프로그램을 돌리는 프로젝트죠. 흥미로운 장난감처럼 보일 수 있지만, 이 글에서 다루는 **브라우저 내 스레드 블로킹(Thread Blocking)** 문제는 프론트엔드와 WASM을 깊게 파고드는 시니어 엔지니어라면 반드시 짚고 넘어가야 할 아키텍처적 난제입니다.

### 블로킹할 것인가, 말 것인가 (To block or not to block)

웹 환경의 절대적인 대원칙이 하나 있습니다. 메인 스레드를 블로킹해서는 안 된다는 것이죠.

과거 저자(Evan)는 `retrowin32` 프로젝트에서 이 문제를 해결하기 위해 에뮬레이터가 명령어를 조금 실행하고 다시 브라우저로 제어권을 넘기는(yield) 비동기 방식을 택했습니다. 하지만 15년 넘게 백엔드와 시스템 프로그래밍을 해온 제 경험상, 억지로 모든 것을 비동기로 만드는 것은 결국 기술 부채로 돌아옵니다.

- **콜백 지옥과 라이프타임:** 모든 Windows API 구현이 async로 변이되어야 합니다.
- **디버깅의 악몽:** 스택 트레이스가 끊어지고 객체의 라이프타임을 추적하기 극도로 어려워집니다.
- **성능 오버헤드:** 타이트한 루프에서도 컨텍스트 스위칭과 제어 오버헤드가 발생합니다.

그래서 Theseus 프로젝트에서는 과감하게 전면 동기식(Synchronous) 방식을 채택하고, 실제 OS 스레드(여기서는 Web Worker)를 사용해 스레드를 에뮬레이션했습니다. 결과적으로 소스 프로그램과 에뮬레이터 코드를 관통하는 깔끔한 스택 트레이스를 얻을 수 있었죠. 디버깅 경험 측면에서는 압도적인 승리입니다.



### 브라우저에서 우아하게 블로킹하기: Atomics와 Shared Memory

메인 스레드는 블로킹할 수 없지만, Web Worker는 블로킹이 가능합니다. 에뮬레이터(Worker)가 브라우저(Main Thread)의 리소스가 필요할 때, `postMessage`를 보내고 메인 스레드가 작업을 마칠 때까지 Worker를 대기시켜야 합니다.

이를 위해 저자는 `SharedArrayBuffer`와 **Atomics API** 를 활용했습니다. 사실상 브라우저 위에 유저 스페이스 Futex를 구현한 셈입니다. 코드를 보시죠.

```rust
fn blocking_call() {
    let mut buf = 0i32;
    let msg = create_message(
        /* ... 실행할 함수 정보 ... */,
        // 로컬 변수 'buf'의 메모리 주소를 넘김
        &mut buf as *mut _ as u32
    );
    post_message(msg);
    unsafe {
        // Atomics notify가 올 때까지 영원히(-1) 대기
        wasm32::memory_atomic_wait32(&mut buf, 0, -1);
    }
}
```

메인 스레드(JS)에서는 메시지를 처리한 후 공유 메모리를 수정해 Worker를 깨웁니다.

```javascript
window.onmessage = (e) => {
    const msg = e.data;
    // ... 메시지 처리 ...
    // msg.buf를 공유 메모리 내의 포인터로 해석:
    const ints = new Int32Array(sharedMemory.buffer, msg.buf, 1);
    ints[0] = 1; // 처리 완료 마킹
    
    // 대기 중인 스레드를 깨움:
    Atomics.notify(ints, 0, 1);
}
```

이 접근법의 백미는 제로 카피(Zero-copy) 입니다. Worker가 렌더링한 픽셀 버퍼의 포인터만 메인 스레드로 넘기면, 메인 스레드는 메모리 복사 없이 해당 버퍼를 직접 읽을 수 있습니다. 과거 C++로 무거운 연산 서버를 짤 때 자주 쓰던 락프리 큐(Lock-free queue) 패턴이 브라우저 위에서 돌아가는 걸 보니 묘한 쾌감이 듭니다.

### 이상과 현실: Rust WASM 생태계의 민낯

이 훌륭한 아키텍처에도 불구하고, 저자는 몇 가지 뼈아픈 현실을 고백합니다. 그리고 저 역시 이 부분에서 크게 공감했습니다.

1. **Rust 표준 라이브러리의 한계:** WASM 타겟의 Rust `std`는 기본적으로 Atomics를 지원하지 않습니다. 이를 해결하려면 Nightly 컴파일러를 써서 표준 라이브러리를 통째로 다시 빌드해야 합니다. 프로덕션 환경에서 Nightly 컴파일러에 의존하는 것은 시한폭탄을 안고 가는 것과 같습니다.
2. **DOM 접근의 번거러움:** Rust Worker에서 브라우저 DOM에 접근하는 것은 여전히 투박합니다. 저자는 결국 호스트 코드를 TypeScript로 작성해 벽을 쳤습니다. 디버깅 도구나 생태계를 고려하면 프론트엔드에서는 여전히 TS가 왕입니다.
3. **직렬화 오버헤드:** 복잡한 객체를 Worker와 Main Thread 간에 넘기는 것은 여전히 숙제입니다. HN 댓글에서도 언급되었듯 `rkyv` 같은 Zero-copy 직렬화 라이브러리가 대안이 될 수 있겠지만, 구조적 복잡도는 피할 수 없습니다.

### Hacker News의 반응과 나의 생각

Hacker News 스레드에서도 꽤 수준 높은 토론이 오갔습니다.

가장 눈에 띄는 피드백은 **OffscreenCanvas** 의 활용입니다. 현재 메인 스레드가 렌더링을 돕고 있다면, 아예 Worker 스레드에서 `OffscreenCanvas`를 통해 메인 스레드 개입 없이 화면에 직접 렌더링하는 것이 훨씬 현대적인 접근일 것입니다.

또한, WASM Component Model(0.3.x)과 최근 LLVM에 병합된 스레딩 관련 PR들이 언급되었습니다. WASM 생태계가 빠르게 발전하고 있다는 증거지만, 역설적으로 "아직 스레딩은 공사 중"이라는 방증이기도 합니다. LibreOffice WASM 포팅이 50MB에 달하는 와중에, 이 프로젝트가 1MB 내외로 최적화되었다는 점은 많은 엔지니어들의 찬사를 받았습니다.

### 결론 (Verdict)

그래서, WASM으로 무거운 멀티스레드 애플리케이션을 당장 포팅해야 할까요?

제 대답은 **아직은 시기상조** 입니다. Figma가 WASM 기반 앱을 만들면서도 네이티브 빌드를 폴백(Fallback)으로 유지했던 전략은 여전히 유효합니다. Shared Memory와 Web Worker를 활용한 아키텍처는 기술적으로 아름답지만, Nightly 컴파일러에 의존해야 하는 Rust 생태계와 직렬화의 한계는 비즈니스 로직에 집중해야 할 엔지니어들의 발목을 잡을 것입니다.

하지만 Theseus 프로젝트는 우리가 앞으로 마주할 웹 플랫폼의 한계와 이를 돌파하는 엔지니어링의 정수를 보여줍니다. 프론트엔드의 성능 한계를 고민하는 분들이라면, 이 코드를 꼭 한번 뜯어보시길 권합니다.
