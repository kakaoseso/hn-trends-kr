솔직히 말해, '프롬프트 몇 줄로 백엔드를 완성했다'는 류의 데모는 이제 지겹습니다. 15년 동안 백엔드 아키텍처를 설계하고 다양한 시스템을 운영해 온 입장에서 보면, 장난감 프로젝트가 아닌 실무 프로덕션 환경에 AI 에이전트를 투입했을 때 아키텍처가 엉망이 되는 경우를 수없이 목격했기 때문입니다.

최근 아카이브(arXiv)에 공개된 "Constraint Decay: The Fragility of LLM Agents in Backend Code Generation" 논문은 제가 현업에서 느끼던 답답함을 정확한 데이터로 증명해 주었습니다. 오늘은 이 논문의 핵심 내용과 Hacker News의 반응, 그리고 시니어 엔지니어로서의 제 개인적인 견해를 정리해 보겠습니다.

## 제약 붕괴(Constraint Decay) 현상의 실체

논문은 80개의 신규 프로젝트(Greenfield)와 20개의 기능 구현 작업을 8개의 웹 프레임워크 환경에서 테스트했습니다. 그리고 매우 흥미로운 현상을 발견합니다. 바로 **제약 붕괴(Constraint Decay)** 입니다.

에이전트에게 단순한 기능 구현(Functional requirements)만 요구할 때는 꽤 훌륭한 코드를 만들어냅니다. 하지만 아키텍처 패턴, 데이터베이스, ORM 같은 구조적 제약(Structural constraints)이 추가될수록 에이전트의 성능은 급격히 하락합니다. 논문에 따르면, 완전히 명세된 작업(Fully specified tasks)으로 갈수록 Assertion Pass Rate가 평균 30점이나 폭락했습니다.

프레임워크에 따른 민감도(Framework sensitivity)도 주목할 만합니다.
- **Minimal Framework:** Flask 같이 가볍고 명시적인 프레임워크에서는 에이전트가 꽤 높은 성공률을 보입니다.
- **Convention-heavy Framework:** FastAPI나 Django처럼 지켜야 할 내부 규칙과 컨벤션이 무거운 환경에서는 성능이 처참하게 무너집니다.

가장 빈번하게 발생하는 에러의 근본 원인은 데이터 레이어 결함이었습니다. 잘못된 쿼리 조합이나 ORM 런타임 위반이 쏟아져 나온 것이죠.

## 왜 이런 일이 발생할까? 최적화의 충돌

Hacker News의 한 유저가 남긴 코멘트가 이 현상의 본질을 정확히 꿰뚫고 있습니다.

> "두 가지 다른 목표를 동시에 최적화할 수는 없습니다. 기능적 요구사항만 있다면 이는 일종의 프로그램 합성(Program synthesis)이며, RL(강화학습)이 이를 강하게 최적화할 수 있습니다. 하지만 비기능적 요구사항이 섞이는 순간, 모델에게는 불완전한 스펙이 주어지는 셈이고 결국 사용자의 의도를 추측해야만 합니다."

격하게 공감합니다. LLM은 본질적으로 다음 토큰을 예측하는 모델입니다. 기능이 동작하도록 만드는 것과, 우리 팀의 복잡한 Django ORM 컨벤션을 맞추는 것은 완전히 다른 차원의 문제입니다. 제약이 많아질수록 컨텍스트 윈도우는 빠르게 채워지고, 결국 모델은 초기 지시사항을 잊어버리는 **Context Rot** 현상에 빠지게 됩니다.

## 우리는 어떻게 대처해야 하는가? (실무적 관점)

그렇다면 이 한계를 어떻게 극복할 수 있을까요? HN 커뮤니티의 토론과 제 실무 경험을 바탕으로 몇 가지 인사이트를 정리해 보았습니다.

- **마크다운 가이드 대신 실제 코드를 주입하라:** Redis의 창시자 Antirez가 언급했듯, 모델에게 "이런 스타일로 짜줘"라며 장황한 마크다운 문서를 주는 것은 비효율적입니다. 대신 "이 파일의 스타일과 패턴을 참고해서 작성해"라고 잘 짜여진 실제 코드 파일(Example)을 컨텍스트에 밀어 넣는 것이 훨씬 강력한 결과를 냅니다.
- **그린필드보다 레거시 환경이 더 유리할 수 있다:** 백지상태(Greenfield)에서 에이전트에게 백엔드를 통째로 짜라고 하면 구조가 무너집니다. 오히려 엄격한 인터페이스와 추상화가 이미 구현되어 있는 레거시 코드베이스에서, RAG나 Tool call을 통해 주변 컨텍스트를 촘촘하게 제공할 때 훨씬 정확한 패치가 생성됩니다. 에이전트의 지능보다 **Harness(테스트 및 컨텍스트 제공 환경)** 가 더 중요합니다.
- **정적 타입(Static Typing)의 강력함:** Python이나 JS 같은 동적 타입 언어보다 Go 언어처럼 정적 타입이 강제되는 환경에서 에이전트의 생산성이 훨씬 높습니다. 컴파일러가 강력한 가드레일 역할을 해주기 때문에, 에이전트가 스스로 에러를 발견하고 수정(Self-correction)하기가 훨씬 수월해집니다.

## 결론 및 총평

생성형 AI 시대가 도래하면서 역설적이게도 **전통적인 소프트웨어 엔지니어링의 가치** 가 더욱 빛을 발하고 있습니다. 모듈화된 설계, 명확한 인터페이스, 점진적 개발(Incremental development), 그리고 강력한 자동화 테스트. 이것들이 갖춰지지 않은 스파게티 코드는 사람도 이해하기 힘들지만, LLM은 더더욱 이해하지 못합니다.

현재의 LLM 코딩 에이전트는 아키텍처를 처음부터 설계할 수 있는 시니어 엔지니어가 아닙니다. 명확한 바운더리와 촘촘한 컨텍스트를 제공했을 때, 지치지 않고 코드를 타이핑해 주는 '초고속 주니어 개발자'에 가깝습니다.

프로덕션 환경에 에이전트를 투입하고 싶다면, 모델의 성능을 탓하기 전에 우리의 코드베이스가 에이전트가 소화할 수 있을 만큼 충분히 모듈화되어 있는지, 그리고 구조적 제약을 검증할 수 있는 자동화된 테스트 파이프라인이 존재하는지 먼저 점검해야 할 것입니다.
