보안 엔지니어링에서 가장 두려운 순간은 언제일까? 아마도 전 세계 25억 대의 기기에서 구동되는 코어 암호화 모듈에 새로운 코드를 푸시할 때일 것이다. 버그 하나가 수십억 명의 개인정보를 위협할 수 있는 환경에서는 '테스트를 통과했다'는 말로는 충분하지 않다.

최근 애플이 iMessage에 양자 내성 암호(PQC)를 도입하며 자사의 corecrypto 라이브러리에 대한 정형 검증(Formal Verification) 청사진을 공개했다. 단순히 '우리가 이렇게 안전하게 만들었다'는 PR용 글이 아니다. 실무에서 마주하는 성능 최적화와 수학적 무결성 사이의 딜레마를 어떻게 엔지니어링으로 풀어냈는지 보여주는 훌륭한 레퍼런스다.

15년 넘게 백엔드와 인프라를 다루면서 수많은 암호화 라이브러리의 흥망성쇠를 지켜본 입장에서, 이번 애플의 접근 방식은 꽤나 인상적이다. 이들이 어떻게 FIPS 203(ML-KEM)과 FIPS 204(ML-DSA) 알고리즘을 C와 ARM64 어셈블리로 구현하고 이를 수학적으로 증명했는지 깊게 파보자.

## 왜 일반적인 테스트로는 부족한가?

'Don't roll your own crypto(자신만의 암호화 알고리즘을 만들지 마라)'는 업계의 불문율이다. 하지만 애플 규모의 기업은 하드웨어의 영혼까지 끌어모아 성능을 쥐어짜야 한다. 

애플은 이식성을 위해 먼저 C로 코드를 작성한 뒤, Apple Silicon의 성능을 극대화하기 위해 ARM64 어셈블리로 주요 루틴을 핸드튜닝(Hand-optimized)한다. 이 과정에서 타이밍 사이드 채널 공격을 막기 위해 DIT(Data Independent Timing)를 적용하고, 메모리 오염을 막기 위해 PAC(Pointer Authentication) 같은 하드웨어 기능을 활용한다. 

문제는 여기서 발생한다. 다항식 연산이나 큰 수의 덧셈 같은 복잡한 수학적 연산을 어셈블리 레벨에서 최적화하다 보면, 캐리(carry)나 빌림(borrow) 처리에서 미세한 산술 버그가 발생하기 쉽다. 이러한 버그는 너무 깊은 곳에 숨어 있어서 기존의 단위 테스트나 Fuzzing으로는 잡아내기 거의 불가능하다.

## 애플의 커스텀 정형 검증 파이프라인

정형 검증은 코드가 수학적 사양(Specification)과 정확히 일치함을 수학적으로 증명하는 기법이다. 하지만 기존의 도구들은 C와 ARM64가 혼재된 프로젝트를 한 번에 검증하지 못하거나, 최신 암호학의 복잡한 수학을 표현하기엔 역부족이었다. 그래서 애플은 기존 도구들을 조합해 자신들만의 파이프라인을 구축했다.



위 다이어그램에서 볼 수 있듯, 이들의 접근법은 매우 체계적이고 실용적이다.

- **1단계:** 이식성 높은 C 코드를 Cryptol(Galois에서 개발한 도메인 특화 언어) 모델로 수동 변환한다.
- **2단계:** SAW(Software Analysis Workbench)를 사용해 C 코드와 Cryptol 모델이 일치하는지 검증한다.
- **3단계:** Galois와 협력하여 만든 cryptol-to-isabelle 도구를 통해 Cryptol 모델을 Isabelle(강력한 수학적 증명 어시스턴트)로 자동 변환한다.
- **4단계:** NIST의 FIPS 사양을 Isabelle로 수동 번역한 뒤, 구현체와 사양이 완벽히 동일함을 5만 개 이상의 증명 단계를 거쳐 입증한다.
- **5단계:** 마지막으로, 최적화된 ARM64 어셈블리 루틴이 이미 검증된 C 루틴과 동일하게 동작함을 Isabelle 내에서 증명한다.

## 코드 레벨에서의 차이: C vs Isabelle

이 과정이 실제로 어떻게 생겼는지 코드를 보면 이해가 쉽다. 다항식의 계수를 더하는 단순한 C 루틴은 다음과 같다.

```c
void ccmlkem_poly_add(int16_t coeffs[CCMLKEM_N], const int16_t a[CCMLKEM_N], const int16_t b[CCMLKEM_N]){
    for (unsigned i = 0; i < CCMLKEM_N; i++) {
        coeffs[i] = a[i] + b[i];
    }
}
```

이를 검증하기 위한 Isabelle 사양은 훨씬 추상적이다. 배열의 크기나 워드의 정확한 비트 수를 명시하지 않고, 루프 대신 map2 연산을 사용해 본질적인 '수학적 의미'만을 정의한다.

```isabelle
definition poly_add :: "'a word list \Rightarrow 'a word list \Rightarrow 'a :: len word list" where
"poly_add xs ys = map2 (+) xs ys"
```

어셈블리 명령어 시퀀스를 곧바로 이 추상적인 수학 공식과 비교하는 것은 미친 짓이다. 애플이 중간에 C 코드를 징검다리로 삼은 것은 엔지니어링 관점에서 매우 영리한 선택이었다.

## 해커뉴스 커뮤니티의 반응과 나의 생각

이 글이 해커뉴스에 올라왔을 때 커뮤니티의 반응도 꽤나 뜨거웠다. 특히 눈에 띄는 의견들이 몇 가지 있었다.

한 유저는 "SAW와 Cryptol은 다른 정형 검증 도구들에 비해 놀랍도록 사용하기 쉽다. 고신뢰성(High-assurance) 분야에서 C++가 여전히 쓰이는 건 안타깝다. C에 비해 안전한 코드를 작성하기 위한 툴링이 너무 부족하기 때문"이라고 지적했다. 전적으로 동의한다. 복잡한 객체 지향 추상화가 들어간 C++ 코드를 정형 검증하는 것은 악몽에 가깝다. 암호화폐나 코어 인프라 레벨에서 여전히 C나 Rust가 선호되는 이유이기도 하다.

가장 인상 깊었던 부분은 애플이 ML-DSA 초기 구현에서 **'누락된 단계(missing-step)' 버그** 를 찾아냈다는 대목이다. 해커뉴스의 다른 유저도 언급했듯, 이는 정형 검증이 빛을 발하는 완벽한 사례다. 코드 리뷰를 할 때 누락된 코드는 눈에 보이지 않기 때문에 다음 줄이 정상 같아 보이면 그냥 넘어가기 십상이다. 극히 드문 입력값에서만 범위 초과 오류를 일으키는 이런 버그는, 누군가 우연히 정확한 입력값을 Fuzzer에 넣지 않는 이상 프로덕션에서 터지기 전까지 절대 발견되지 않는다.

## 결론: 정형 검증은 이제 장난감이 아니다

솔직히 말해, 일반적인 B2C 웹 서비스나 CRUD 앱을 만들면서 Isabelle이나 SAW를 도입할 필요는 없다. ROI가 전혀 맞지 않는다. 하지만 당신이 수억 명이 사용하는 운영체제, 암호화폐 지갑, 혹은 자율주행 자동차의 코어 모듈을 개발하고 있다면 이야기는 달라진다.

과거 정형 검증은 학계의 상아탑 안에 갇혀 있는, 실무와는 동떨어진 기술로 여겨졌다. 하지만 애플이 이번에 Cryptol-to-Isabelle 번역기와 관련 라이브러리들을 오픈소스로 공개하면서, 고신뢰성 소프트웨어를 개발하는 업계 전체의 기준이 한 단계 높아졌다고 본다.

당장 내일 출근해서 정형 검증을 파이프라인에 추가할 수는 없겠지만, 소프트웨어의 '정확성'을 보장하는 방법론이 단위 테스트를 넘어 수학적 증명의 영역으로 대중화되고 있다는 사실만큼은 시니어 엔지니어로서 반드시 주시해야 할 흐름이다.
