정수를 문자열로 변환하는 데 CPU 사이클이 얼마나 낭비되는지 심각하게 고민해 본 적이 있는가? 대규모 트래픽을 처리하는 백엔드 시스템, 특히 JSON 직렬화나 고주파 트레이딩(HFT)의 로깅 구간에서 `itoa`(Integer to ASCII) 연산은 생각보다 훨씬 거슬리는 병목이다.

최근 Wiley에 정수를 십진수 문자열로 변환하는 데 **2나노초(ns)** 미만이 걸린다는 논문이 올라왔다. 2나노초라니, L1 캐시 히트 레이턴시와 맞먹는 속도다. 처음 이 제목을 봤을 때 내 반응은 "또 SIMD 매직 넘버 장난질이겠군" 이었다. 그리고 역시나, 이들은 AVX-512 명령어 셋을 영혼까지 끌어모아 이 미친 Throughput을 달성했다.

## 어떻게 2나노초의 벽을 깼는가?

전통적인 `itoa` 구현은 느리다. 루프를 돌면서 10으로 나누고, 나머지를 구하고, ASCII 오프셋('0')을 더하는 과정을 반복한다.

```cpp
// 우리가 흔히 아는 느린 방식
while (num > 0) {
    *--ptr = '0' + (num % 10);
    num /= 10;
}
```

이 방식의 치명적인 문제는 CPU가 가장 싫어하는 연산인 '나눗셈(Division)'이 포함되어 있다는 것과, 이전 계산이 끝나야 다음 계산을 할 수 있는 데이터 의존성(Data dependency) 때문에 파이프라인이 제대로 돌지 않는다는 점이다.

이 논문의 핵심은 나눗셈을 곱셈과 비트 시프트(Bit shift)로 치환하고, 이를 AVX-512 레지스터(512-bit)에 올려 여러 자리의 숫자를 한 번에 병렬로 처리(Vectorization)하는 것이다. 2018년쯤 내가 몸담았던 팀에서 금융 시계열 데이터를 파싱할 때 SSE4.1과 AVX2를 이용해 비슷한 최적화를 시도한 적이 있다. 당시에도 엄청난 성능 향상을 봤지만, AVX-512는 한 번에 64바이트를 처리할 수 있으니 차원이 다른 Throughput이 나오는 것은 당연하다.

## Hacker News의 반응과 AVX-512의 딜레마

하지만 이 기술이 당장 내일 우리의 프로덕션 코드를 바꿀 수 있을까? Hacker News의 한 유저(anon)가 아주 정확한 지적을 했다.

> "이 디자인은 AVX-512 명령어 셋을 활용합니다. 하지만 AVX-512는 최신 Intel 컨슈머 CPU, 특히 Alder Lake 시리즈부터 BIOS 업데이트를 통해 완전히 비활성화되며 단종 수순을 밟고 있습니다."

이게 바로 현재 하드웨어 생태계의 가장 큰 코미디다. Intel은 P-core와 E-core를 섞어 쓰는 하이브리드 아키텍처를 도입하면서, 두 코어 간의 명령어 셋 일관성을 맞추기 위해 컨슈머 라인업에서 AVX-512를 날려버렸다. 반면 AMD는 Zen 4부터 AVX-512를 아주 훌륭하게 지원하고 있다.

엔지니어 입장에서 이는 끔찍한 파편화(Fragmentation)를 의미한다. 서버(Xeon, EPYC)에서는 AVX-512가 빵빵하게 돌아가지만, 개발자들의 로컬 머신(Intel 랩탑이나 Apple Silicon)에서는 돌아가지 않는다. 결국 이 2나노초짜리 코드를 쓰려면 CPU ID를 체크해서 AVX-512, AVX2, ARM NEON, 그리고 Fallback 스칼라 코드까지 런타임 디스패처(Runtime dispatcher)를 주렁주렁 달아야 한다.

## 결론: 그래서 써야 하는가?

솔직히 말하자면, 당신이 `fmt` 라이브러리 메인테이너이거나 `simdjson` 같은 극단적인 성능의 파서를 개발하는 사람이 아니라면 이 코드를 직접 짤 일은 없다.

하지만 이 논문이 시사하는 바는 명확하다. 우리가 당연하게 여기는 표준 라이브러리의 기저에는 아직도 최적화할 여지가 엄청나게 남아있다는 것이다. 서버 환경에서의 SIMD 최적화는 여전히 강력한 무기다. 비록 Intel이 컨슈머 시장에서 AVX-512를 버렸을지언정, 백엔드 엔지니어라면 데이터 병렬 처리가 어떻게 Latency를 극한으로 끌어내리는지 그 원리만큼은 반드시 이해하고 있어야 한다.
