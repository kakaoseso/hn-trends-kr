"C 언어는 이식성이 뛰어나다." 내가 주니어 시절 귀에 못이 박히도록 들었던 말이다. 하지만 15년 넘게 시스템 프로그래밍과 컴파일러 주변을 맴돌며 깨달은 진실은 조금 다르다. 100% ISO C 표준만 준수하는 실무 코드는 유니콘과 같다. 이론상으로는 존재하지만 현실에서는 아무도 본 적이 없다.

최근 Hacker News에서 흥미로운 글을 하나 읽었다. 새로운 C 컴파일러를 작성 중인 한 개발자가 시스템 헤더 파일들을 파싱하면서 겪은 기괴한 경험담을 공유한 글이다. 이 글을 읽으며 내가 과거 크로스 플랫폼 빌드를 세팅하며 밤을 새웠던 기억들이 플래시백처럼 스쳐 지나갔다. 

솔직히 말하자면, 오늘날의 C 생태계는 표준 C가 아니라 'GCC 방언(Dialect)'이 지배하고 있다. 새로운 C 컴파일러를 만들고 싶다면, 당신이 가장 먼저 해야 할 일은 컴파일러를 잘 만드는 것이 아니라 당신의 컴파일러가 GCC인 것처럼 시스템을 속이는 것이다.

### Glibc와 헤더 지옥 (Header Hell)

어떤 C 컴파일러든 가장 먼저 통과해야 할 관문은 `<stdio.h>`를 파싱하고 Hello World를 찍는 것이다. 리눅스 환경이라면 이는 필연적으로 glibc와의 격투를 의미한다.

glibc는 나름대로 GCC 외의 컴파일러를 배려하려 노력했지만, 그 결과물인 `sys/cdefs.h`는 끔찍한 괴물이 되어버렸다. 아래 코드를 보자.

```c
/* GCC, clang, and compatible compilers have various useful declarations
that can be made with the '__attribute__' syntax. All of the ways we use
this do fine if they are omitted for compilers that don't understand it. */
#if !(defined __GNUC__ || defined __clang__ || defined __TINYC__)
# define __attribute__(xyz) /* Ignore */
#endif
```

이 코드는 말 그대로 코미디다. 만약 당신이 새로운 컴파일러를 만들었고, 힘들게 `__attribute__((packed))` 같은 GNU 확장을 완벽하게 구현했다고 치자. 하지만 당신의 컴파일러 이름이 GCC, Clang, TCC 중 하나가 아니라면? glibc는 당신의 노력을 비웃으며 모든 attribute를 빈 공백으로 치환해버린다. 

결국 리눅스 환경에서 ABI를 깨지 않고 `epoll_event` 같은 구조체를 제대로 처리하려면, 당신의 컴파일러는 울며 겨자 먹기로 `#define __GNUC__`를 선언해서 자신이 GCC인 척해야 한다. Clang조차도 초창기에 리눅스 커널을 빌드하기 위해 자신을 GCC 4.2.1 버전으로 위장해야만 했다.

### 인라인(Inline) 시맨틱과 매크로 스파게티

C99 이전의 GNU89 인라인 시맨틱과 C99의 표준 인라인 시맨틱이 충돌한다는 사실은 C 개발자들에게 잘 알려진 골칫거리다. 하지만 이를 해결하기 위해 오픈소스 프로젝트들이 도입한 Workaround를 보면 한숨이 절로 나온다.

Gnulib의 `extern-inline.m4` 파일에 있는 호환성 매크로를 보자.

```c
#if (((defined __APPLE__ && defined __MACH__) \
|| defined __DragonFly__ || defined __FreeBSD__) \
&& (defined HAVE___HEADER_INLINE \
? (defined __cplusplus && defined __GNUC_STDC_INLINE__ \
&& ! defined __clang__) \
: ((! defined _DONT_USE_CTYPE_INLINE_ \
&& (defined __GNUC__ || defined __cplusplus)) \
|| (defined _FORTIFY_SOURCE && 0 < _FORTIFY_SOURCE \
&& defined __GNUC__ && ! defined __cplusplus))))
# define _GL_EXTERN_INLINE_STDHEADER_BUG
#endif
```

이게 정녕 사람이 유지보수하라고 만든 코드인가? 각종 OS, 컴파일러 종류, C++ 여부, 심지어 특정 버그의 존재 여부까지 매크로로 탐지하려다 보니 코드가 스파게티를 넘어선 무언가가 되었다. 이런 코드를 마주할 때마다 나는 C/C++ 생태계가 얼마나 아슬아슬한 모래성 위에 서 있는지 실감한다.

### 잘못된 Feature Detection

SDL의 `SDL_endian.h` 사례도 흥미롭다. 이들은 최적화를 위해 내장 함수(Built-in)나 인라인 어셈블리를 사용하려 하는데, 그 로직이 참으로 기가 막힌다. 컴파일러가 `__has_builtin(__builtin_bswapX)`를 지원한다고 명시해도, 아키텍처가 `__x86_64__`로 선언되어 있고 컴파일러가 GCC/Clang이 아니면 무조건 확장 인라인 어셈블리를 타도록 강제한다. 

표준적인 Feature Detection 메커니즘을 제공해도, 레거시 프로젝트들이 자신들만의 하드코딩된 조건문으로 이를 무시해버리는 것이다.

### Hacker News의 반응: 곪아 터진 불만들

이 글에 대한 HN 커뮤니티의 반응은 뜨거웠다. 특히 윈도우나 FreeBSD 환경을 주로 다루는 개발자들의 불만이 폭발했다.

- **Linux-centricity:** 많은 C 프로젝트들이 사실상 "내 리눅스 머신에서는 잘 돌아감" 수준으로 작성되어 있다. POSIX 표준을 지킨다고 하지만 은연중에 glibc나 시스템디(systemd)의 비표준 동작에 의존하는 경우가 허다하다.
- **Walter Bright의 증언:** D 언어의 창시자인 Walter Bright 역시 D 컴파일러에 ImportC(C 컴파일러 내장 기능)를 구현할 때, 이 미쳐버린 헤더 파일들의 "nutburger nonsense"를 우회하느라 엄청난 시간을 낭비했다고 토로했다.
- **Edge cases:** slimcc 컴파일러 개발자는 실무 프로젝트를 컴파일하며 겪은 기상천외한 버그들을 공유했다. `math.h`의 NAN이 `(0.0f / 0.0f)`로 fallback 되면서 printf가 `nan` 대신 `-nan`을 출력해 테스트가 깨지거나, `if(0) { undefined_function() }`를 사용해 `static_assert`를 야매로 흉내 내는 프로젝트 등, 실무 C 코드는 그야말로 지뢰밭이다.

### 결론: 우리는 어디로 가야 하는가

솔직히 말해서, 새로운 C 컴파일러를 바닥부터 작성하는 것은 기술적인 도전이라기보다는 고고학적 발굴 작업에 가깝다. 과거의 잘못된 설계, 특정 컴파일러 버전에 종속된 버그들, 그리고 이를 덮기 위해 덧대어진 수많은 매크로 패치들을 리버스 엔지니어링해야 하기 때문이다.

컴파일러 제작자의 입장에서 현실적인 해결책은 단 하나다. **자존심을 버리고 GCC인 척하는 것.** `__GNUC__`를 정의하고 그들의 확장 기능들을 묵묵히 구현하는 수밖에 없다. 

하지만 생태계 전체를 본다면 이는 비극이다. 우리는 언제까지 `#ifdef __GNUC__`에 의존할 것인가? C 표준 위원회와 오픈소스 메인테이너들은 이제 컴파일러의 종류나 버전을 체크하는 구시대적인 방식에서 벗어나, `__has_builtin`, `__has_feature` 같은 기능 기반의 Feature Test Macro로 완전히 넘어가야 한다.

C 언어는 강력하지만, 그 생태계의 파편화는 점점 임계점에 다다르고 있다. 차세대 시스템 언어들(Rust, Zig 등)이 훌륭한 패키지 매니저와 일관된 빌드 시스템으로 무장하고 치고 올라오는 지금, C 생태계도 이런 레거시의 사슬을 끊어내지 못한다면 결국 '레거시 유지보수용 언어'로 전락하고 말 것이다.
