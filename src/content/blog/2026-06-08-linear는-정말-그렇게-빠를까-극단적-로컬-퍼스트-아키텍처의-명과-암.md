최근 몇 년간 프론트엔드 커뮤니티에서 Linear의 성능에 대한 찬양을 심심치 않게 볼 수 있다. 클릭하자마자 즉각적으로 반응하는 UI, 지연 없는 이슈 생성 등 Linear가 제공하는 사용자 경험은 확실히 인상적이다. 하지만 15년 넘게 현업에서 수많은 아키텍처의 흥망성쇠를 지켜본 엔지니어로서, 나는 '마법 같은 은환탄'은 없다는 것을 잘 알고 있다. 

최근 Dennis Brotzky가 작성한 Linear의 기술적 해부 글과 이에 대한 해커뉴스(Hacker News)의 열띤 토론을 지켜보며, 이들이 어떻게 극한의 성능을 쥐어짜 냈는지, 그리고 그 이면에 숨겨진 트레이드오프와 맹점은 무엇인지 깊게 파헤쳐보고자 한다.

## 브라우저를 데이터베이스로: 로컬 퍼스트와 낙관적 업데이트

대부분의 웹 애플리케이션은 동일한 굴레에 빠져 있다. 사용자가 클릭하면 브라우저가 HTTP 요청을 보내고, 서버가 DB를 조회한 뒤 응답을 줄 때까지 스피너(Spinner)를 띄운다. 반면 Linear는 이 관계를 완전히 뒤집었다.

UI가 읽어 들이는 실제 데이터베이스는 브라우저 내부의 IndexedDB에 존재한다. 데이터 변경은 로컬 메모리(MobX)에 먼저 적용되고, 비동기적으로 서버에 푸시된다. 서버는 WebSocket을 통해 다른 클라이언트들에게 델타(Delta)를 브로드캐스트한다.

이 차이를 극명하게 보여주는 코드를 보자.

```javascript
// 전통적인 웹 앱의 서버 업데이트 방식
async function updateIssue({ issue }) {
  showSpinner();
  const response = await fetch(`/api/issues/${issue.id}`, {
    method: "PATCH",
    body: JSON.stringify({ title: issue.title }),
  });
  const updated = await response.json();
  setIssue(updated)
  hideSpinner();
}

// Linear의 방식
issue.title = "Faster app launch";
issue.save();
```

첫 번째 줄에서 메모리 내의 MobX 옵저버블을 업데이트하여 UI를 동기적으로 다시 렌더링한다. 두 번째 줄은 백그라운드에서 서버로 플러시(flush)될 트랜잭션을 큐에 넣는다. 네트워크 I/O를 UI 렌더링 경로에서 완전히 제거한 것이다.

개인적으로 이 접근법 자체는 훌륭하다고 생각한다. 네트워크는 언제나 우리가 통제할 수 없는 가장 큰 병목이다. 하지만 이를 위해 자체적인 동기화 엔진(Sync Engine)을 바닥부터 구축했다는 점은 주목할 만하다. 대부분의 스타트업이 초기 단계에서 시도하기에는 엄청난 오버엔지니어링이 될 수 있다. 해커뉴스 댓글에서도 언급되었듯, 최근에는 Zero나 Replicache 같은 훌륭한 추상화 도구들이 나와 있으니 굳이 바닥부터 짤 필요는 없다.

## 초기 로딩 속도의 비밀: 극단적인 코드 스플리팅과 프리로딩

Linear는 무려 21MB에 달하는 압축된 JavaScript를 클라이언트에 전송한다. 일반적인 SPA라면 로딩 화면에서 수 초간 멈춰있을 용량이다. 이들은 번들러를 Parcel에서 Rollup, Vite, 그리고 최근 Rolldown으로 네 번이나 교체하며 이 문제를 해결했다.

핵심은 레거시 브라우저 지원을 과감히 포기하고 모던 ESM 기반으로 코드를 수백 개의 라우트 레벨 청크로 쪼갠 것이다. 특히 벤더(Vendor) 번들을 단일 파일로 묶지 않고 패키지별로 분리한 전략이 돋보인다.

```javascript
// 패키지별로 청크를 분리하는 Vite 설정 예시
manualChunks(id) {
  if (id.includes("node_modules")) {
    const pkg = id.match(/node_modules\/([^/]+)/)?.[1];
    if (pkg) return `vendor-${pkg}`;
  }
}
```

이렇게 쪼갠 수백 개의 파일은 워터폴(Waterfall) 현상을 막기 위해 `<head>` 태그 내에서 `<link rel=modulepreload>`를 통해 병렬로 로드된다. 이후 사용자가 로그인 페이지에 머무는 동안 서비스 워커(Service Worker)가 나머지 에셋을 백그라운드에서 캐싱한다.

## 인증은 나중에, 렌더링이 먼저다

내가 가장 감탄한 부분은 이들의 초기 App Shell 렌더링과 인증(Auth) 처리 방식이다. 일반적인 앱들은 `/me` API를 호출해 세션을 검증할 때까지 빈 화면을 보여준다. Linear는 다르다.

```javascript
// localStorage에 데이터가 없으면 로그아웃 레이아웃 렌더링
if (localStorage.getItem("ApplicationStore") === null) {
  document.documentElement.classList.add("logged-out");
}
```

이들은 `localStorage`에 데이터가 있다면 일단 'Happy Path'를 가정하고 캐시된 UI를 즉시 그려버린다. 실제 세션 검증은 백그라운드에서 이루어지며, 만약 토큰이 만료되었다면 그때 로그인 페이지로 튕겨낸다. 인라인 CSS와 결합된 이 방식은 사용자가 URL을 입력하고 엔터를 치는 순간 앱이 준비된 것 같은 착각을 불러일으킨다. 프론트엔드 엔지니어라면 반드시 참고해야 할 훌륭한 패턴이다.

## 애니메이션의 기본 원칙 준수

성능을 갉아먹는 주범 중 하나는 잘못된 CSS 애니메이션이다. Linear는 레이아웃 재계산을 유발하는 속성(width, margin 등)은 절대 애니메이션하지 않는다.

```css
/* Linear가 하는 방식 (GPU 컴포지팅) */
.icon-arrow {
  transform: translateX(0);
  transition: transform 0.15s;
}

/* 초보적인 실수 (레이아웃 트리거) */
.row:hover {
  margin-left: 2px;
  transition: all 0.2s;
}
```

오직 `transform`과 `opacity`만 사용하여 GPU에 연산을 위임한다. 또한 전환(transition) 시간을 150ms 이하로 짧게 가져가서 앱이 '스냅(snappy)'하게 느껴지도록 유도한다. 디테일에 대한 집착이 돋보이는 대목이다.

## 해커뉴스의 냉혹한 비판: 은환탄은 없다

여기까지 보면 Linear가 완벽한 아키텍처를 가진 것 같지만, 해커뉴스의 시니어 엔지니어들은 날카로운 비판을 쏟아냈다. 나 역시 이들의 의견에 상당 부분 동의한다.

- **300ms가 정말 기본값인가?:** 원문에서는 전통적인 CRUD 앱이 300ms가 걸린다고 전제했다. 하지만 백엔드를 엣지(Edge)에 배포하거나 지리적으로 라우팅을 잘 설계하면 30ms 이내의 응답도 충분히 가능하다. 물리적인 빛의 속도(네트워크 RTT)를 극복하기 위해 클라이언트에 거대한 분산 시스템(Sync Engine)을 욱여넣는 것이 과연 모든 팀에게 올바른 방향일까? 
- **낙관적 업데이트의 'Sad Path':** 한 사용자는 Linear에서 텍스트를 입력하다가 잠깐 멈추고 다시 입력할 때 데이터가 과거 상태로 롤백되는 현상을 지적했다. 이는 로컬 퍼스트 동기화 모델이 겪는 고질적인 충돌(Conflict) 문제다. 'Happy Path'에서는 번개처럼 빠르지만, 네트워크 지연이나 동시 편집 상황에서 발생하는 데이터 정합성 문제는 사용자에게 극도의 스트레스를 유발한다.
- **과도한 UI 단순화 (Applification):** 깔끔한 UI를 위해 기능과 라벨을 숨기면서 오히려 학습 곡선이 높아졌다는 비판도 많았다. 검색창을 띄우려면 `Ctrl+F`를 눌러야만 하는 등, 키보드 중심의 설계가 마우스 유저나 초보자에게는 꽤 불친절하게 다가온다.
- **리소스 점유율:** Firefox 등 특정 브라우저에서 메모리 누수와 높은 CPU 점유율을 보인다는 리포트도 있었다. 21MB의 JS와 수천 개의 MobX 옵저버블 객체가 메모리에 상주하는 아키텍처의 필연적인 부작용이다.

## 총평: 프로덕션에 도입할 가치가 있는가?

Linear의 아키텍처는 프론트엔드 성능 최적화의 극의를 보여주는 마스터클래스다. 브라우저를 멍청한 렌더러가 아닌 강력한 로컬 클라이언트로 격상시킨 그들의 엔지니어링 역량에는 박수를 보낸다.

하지만 우리 팀의 다음 프로젝트에 이 스택을 도입할 것이냐고 묻는다면, 내 대답은 **'아니오'** 다.

대부분의 B2B SaaS나 CRUD 애플리케이션은 이 정도의 복잡도를 감당할 필요가 없다. React Query나 SWR을 활용한 제한적인 낙관적 업데이트, 그리고 서버 사이드 렌더링(SSR)이나 엣지 컴퓨팅을 적절히 혼합하는 것만으로도 99%의 유저를 만족시킬 수 있는 성능을 뽑아낼 수 있다. Linear처럼 상태 동기화 엔진을 직접 구축하는 것은 그 자체가 거대한 인프라 프로젝트이며, 수많은 엣지 케이스(Sad Path)와의 끝없는 싸움을 의미한다.

기술의 화려함에 매몰되지 말자. Linear가 빠른 이유는 단순히 로컬 퍼스트라서가 아니라, 그들이 수년간 수백 가지의 미세한 성능 병목을 집요하게 찾아내고 개선했기 때문이다. 우리가 배워야 할 것은 그들의 아키텍처 그 자체가 아니라, 사용자 경험을 위해 10ms 단위의 지연조차 허용하지 않으려는 그 집요한 장인정신이다.
