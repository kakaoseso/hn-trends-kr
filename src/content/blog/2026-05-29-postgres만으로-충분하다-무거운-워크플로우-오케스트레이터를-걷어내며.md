15년 넘게 백엔드 엔지니어링을 해오면서 가장 많이 목격한 '오버엔지니어링' 중 하나는 바로 워크플로우 오케스트레이션이다. 어느 순간부터 우리는 단순한 비동기 작업이나 재시도 로직을 처리하기 위해 Temporal, Airflow, 혹은 AWS Step Functions 같은 거대한 시스템을 도입하는 것을 당연하게 여기기 시작했다.

하지만 이런 외부 오케스트레이터를 도입하는 순간, 인프라의 복잡도는 기하급수적으로 증가한다. 최근 DBOS 팀이 발표한 흥미로운 아티클은 이 지점을 정확히 파고든다. 그들의 주장은 단순하고 도발적이다. "Durable execution을 위해 필요한 건 Postgres뿐이다."

솔직히 처음엔 나도 회의적이었다. "또 Postgres를 만능 도구로 쓰려는 시도인가?" 싶었지만, 아티클을 읽고 아키텍처를 뜯어볼수록 내가 과거에 겪었던 수많은 인프라 장애와 그 해결책들이 떠올랐다.

### 외부 오케스트레이터의 함정

일반적으로 Durable workflow는 중앙 집중형 오케스트레이터를 통해 구현된다.

![External workflow orchestration system architecture diagram](https://cdn.prod.website-files.com/672411cbf038560468c9e68f/6a0dbd9279898da496135035_f62a8f73.png)

클라이언트가 워크플로우를 요청하면, 오케스트레이터가 이를 데이터 스토어에 기록하고 워커(Worker)에게 할당한다. 워커가 작업을 마치면 다시 오케스트레이터에게 결과를 보고하고, 다음 스텝이 진행된다.

이론상으로는 완벽해 보인다. 하지만 실무에서는 어떨까? 오케스트레이터 자체가 거대한 단일 장애점(SPOF)이 된다. Temporal 클러스터를 운영해 본 사람이라면 알겠지만, 상태 관리를 위한 DB와 Temporal 서버 자체의 버전을 맞추고 스케일링하는 작업은 전담 데브옵스 엔지니어가 필요할 정도로 고된 일이다. 결국 비즈니스 로직보다 인프라 유지보수에 더 많은 시간을 쏟게 된다.

### Postgres-backed Durable Execution: 단순함의 미학

DBOS가 제안하는 방식은 이 중앙 오케스트레이터를 완전히 제거하고, 그 역할을 우리가 이미 가장 잘 이해하고 있는 Postgres에 맡기는 것이다.

![Postgres-backed durable execution system architecture diagram](https://cdn.prod.website-files.com/672411cbf038560468c9e68f/6a0dbd9279898da496135032_7bffa8dc.png)

애플리케이션 서버(워커)들은 별도의 미들웨어 없이 Postgres와 직접 통신한다. Postgres의 테이블이 큐(Queue) 역할을 하고, 워커들은 이 테이블을 폴링(polling)하여 작업을 가져간다.

여기서 핵심은 동시성 제어다. 여러 워커가 동시에 같은 작업을 가져가는 것을 막기 위해 Postgres의 강력한 락 매커니즘을 사용한다. 아티클에서는 구체적인 쿼리를 명시하지 않았지만, 실무에서 이런 패턴을 구현할 때 십중팔구 사용하는 것은 `FOR UPDATE SKIP LOCKED` 구문이다.

```sql
SELECT workflow_id, payload
FROM workflows
WHERE status = 'PENDING'
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

이 방식은 내가 2018년 대규모 결제 시스템의 재시도 로직을 설계할 때 사용했던 패턴과 정확히 일치한다. 당시 우리는 복잡한 메시지 브로커를 걷어내고 이 쿼리 하나로 모든 동시성 이슈를 해결했다. 여러 워커가 경합하더라도 락이 걸린 행은 부드럽게 건너뛰기 때문에 병목이 발생하지 않는다.

### 공짜로 얻는 강력한 Observability

이 아키텍처의 또 다른 엄청난 장점은 관측성(Observability)이다. 모든 워크플로우의 상태와 스텝별 결과가 Postgres 테이블에 고스란히 저장된다. 외부 시스템의 복잡한 대시보드를 학습할 필요 없이, 그저 SQL만 작성하면 된다.

![SQL Query to analyze durable workflow execution observability data](https://cdn.prod.website-files.com/672411cbf038560468c9e68f/6a0dbd9279898da49613502f_e0ebb3ff.png)

예를 들어, 지난 한 달 동안 실패한 워크플로우를 찾고 싶다면 다음과 같은 간단한 쿼리로 끝난다.

```sql
SELECT workflow_id, error_message, created_at
FROM workflows
WHERE status = 'ERROR'
  AND created_at >= NOW() - INTERVAL '1 month';
```

이건 정말 강력하다. Key-Value 스토어를 백엔드로 사용하는 오케스트레이터들에서는 이런 식의 분석 쿼리를 실행하는 것이 불가능하거나 극도로 비효율적이다. Postgres의 수십 년 된 쿼리 최적화 엔진과 인덱스를 그대로 활용할 수 있다는 것은 엔지니어링 리소스를 엄청나게 아껴준다.

### Hacker News의 시선과 나의 생각

Hacker News 커뮤니티에서 이런 주제가 나오면 항상 등장하는 단골 멘트들이 있다. "Postgres를 큐로 사용하면 Dead Tuple이 쌓여서 Vacuum이 못 버틴다", "Polling 방식은 Push 방식보다 확장성이 떨어진다" 같은 비판들이다.

물론 일리가 있는 지적이다. 초당 수십만 건의 이벤트를 처리해야 하는 스트리밍 시스템이라면 Kafka나 전용 메시지 큐를 써야 한다. 하지만 가슴에 손을 얹고 생각해 보자. 당신의 서비스가 넷플릭스나 우버 수준의 트래픽을 처리하고 있는가?

대부분의 B2B 서비스나 일반적인 트래픽 규모의 B2C 서비스에서 Postgres는 초당 수만 건의 트랜잭션을 가볍게 씹어 먹는다. DBOS의 벤치마크에서도 단일 Postgres 서버로 초당 수만 개의 워크플로우를 처리하는 것을 증명했다. 인프라의 복잡도를 낮춰서 얻는 안정성과 개발 속도 향상이, 극단적인 엣지 케이스를 대비해 거대한 시스템을 짊어지고 가는 것보다 훨씬 가치 있다.

### 결론 (Verdict)

- **실용성:** 5/5
- **확장성:** 4/5 (초대규모 트래픽 제외)
- **운영 편의성:** 5/5

DBOS가 주장하는 Postgres 기반의 Durable Execution은 단순한 장난감이 아니다. 이는 시스템 아키텍처를 대하는 매우 성숙하고 실용적인 태도다. 이미 데이터베이스로 Postgres를 사용하고 있다면, 시스템에 새로운 실패 지점(Point of Failure)을 추가하지 않고도 강력한 워크플로우 엔진을 얻을 수 있다.

새로운 프로젝트를 시작하거나 기존의 복잡한 오케스트레이터에 지쳤다면, 이 패턴을 도입해 보는 것을 강력히 권장한다. 때로는 가장 지루하고 오래된 기술이 가장 혁신적인 결과를 만들어낸다.
