15년 차 엔지니어로서 단언컨대, 게임 개발에서 유체 시뮬레이션(Fluid Simulation)은 항상 매력적이면서도 지독한 두통을 유발하는 주제다. 물리학의 영역인 Navier-Stokes 방정식을 60 FPS가 돌아가는 실시간 렌더링 환경에 욱여넣는 작업은 결코 만만치 않다.

최근 Hacker News에서 흥미로운 아티클을 하나 발견했다. 한 개발자가 Godot 엔진을 사용해 2D 그리드 기반의 유체 시뮬레이션을 바닥부터 구현하며 그 과정을 상세히 기록한 글이다. AI가 생성한 뻔한 튜토리얼이 넘쳐나는 요즘, Jos Stam의 전설적인 논문 Real-Time Fluid Dynamics for Games를 직접 씹어 삼키고 소화해 낸 이런 날것의 엔지니어링 포스트는 무척 반갑다.

오늘은 이 아티클을 바탕으로, 실시간 유체 시뮬레이션이 내부적으로 어떻게 굴러가는지, 그리고 실무적인 관점에서 이 접근법이 어떤 의미를 가지는지 깊게 파헤쳐보자.

## 우아한 속임수: 안정성을 위한 타협

이 구현체의 핵심은 **정확도** 를 희생하고 **안정성** 과 **성능** 을 취했다는 점이다. 저자는 철저히 교육적 목적을 위해 CPU 기반의 1차원 배열을 사용하여 상태를 관리한다. 

유체 시뮬레이션의 핵심 사이클은 크게 이류(Advection), 확산(Diffusion), 투영(Projection) 세 단계로 나뉜다. 여기서 엔지니어링적으로 가장 흥미로운 부분은 단연 이류(Advection)를 처리하는 방식이다.

### 역추적(Backward Tracking)을 통한 이류 계산

보통 밀도(Density)나 속도(Velocity)를 이동시킨다고 하면, 현재 셀의 값을 속도 벡터가 가리키는 다음 위치로 밀어내는(Push) 방식을 떠올리기 쉽다. 하지만 이 방식은 그리드 밖으로 값이 벗어나거나 특정 셀에 값이 뭉치는 등 수치적 불안정성을 극도로 높인다.

저자는 Jos Stam의 Semi-Lagrangian 기법을 차용하여 시간을 거슬러 올라가는 방식을 택했다.

```gdscript
var x := i - dt0 * u[idx]
var y := j - dt0 * v[idx]
x = clamp(x, 0.5, N + 0.5)
y = clamp(y, 0.5, N + 0.5)
```

현재 셀에서 속도 벡터를 역전시켜 이전 프레임에서 유체가 '어디서 왔을지'를 추적한다. 도착한 좌표는 정확히 셀의 중앙이 아니므로, 주변 4개 셀의 값을 Bilinear interpolation(쌍선형 보간)으로 섞어서 현재 셀의 값을 결정한다. 

솔직히 처음 이 개념을 접했을 때 꽤나 충격을 받았던 기억이 난다. 인과율을 역전시키는 듯한 이 우아한 수학적 꼼수 덕분에, 타임스텝(`delta`)이 아무리 커져도 시뮬레이션이 폭발(Blow-up)하지 않고 무조건적인 안정성을 보장받는다.

### 투영(Projection): 질량 보존의 법칙 강제하기

이류와 확산 단계를 거치고 나면 속도장(Velocity field)은 엉망이 된다. 유체가 한 곳으로 압축되거나 블랙홀처럼 사라지는 아티팩트가 발생한다. 실제 물은 비압축성(Incompressible) 유체이므로 이를 교정해야 한다.

저자는 발산(Divergence) 필드를 계산한 뒤, 이를 상쇄하기 위한 압력(Pressure) 필드를 구한다. 이때 무거운 선형 방정식 시스템을 풀어야 하는데, 실시간 환경에서는 정확한 해를 구하는 것이 불가능하다.

```gdscript
for k in range(20):
    for j in range(1, N + 1):
        for i in range(1, N + 1):
            pressure[IX(i, j)] = (
                divergence[IX(i, j)] +
                pressure[IX(i - 1, j)] +
                pressure[IX(i + 1, j)] +
                pressure[IX(i, j - 1)] +
                pressure[IX(i, j + 1)]
            ) / 4.0
```

대신 Gauss-Seidel 이완법(Relaxation)을 20회 반복하여 그럴싸한 근사치를 얻어낸다. 물리학자들이 본다면 질량 손실이 발생한다며 기겁하겠지만, 우리는 게임 개발자다. 화면에서 시각적으로 유체처럼 보이고 60 FPS가 방어된다면 그것이 곧 정답이다.

## Hacker News 커뮤니티의 날카로운 시선

HN 스레드에서도 이 구현체에 대한 수준 높은 토론이 오갔다. 몇 가지 흥미로운 포인트를 짚어보자.

- **버그 캐치:** 한 유저가 로켓 배기 속도를 더하는 코드에서 `delta` 타임스텝을 곱하는 것을 저자가 누락했음을 지적했다. 저자도 피곤해서 놓쳤다고 인정했는데, 이런 날카로운 코드 리뷰가 바로 오픈소스 커뮤니티의 묘미다.
- **소용돌이(Vortices) 보존:** 기본 구현에서는 유체가 너무 빨리 끈적해지고 소용돌이가 사라지는 현상(Numerical dissipation)이 발생한다. 한 엔지니어는 인위적인 Vorticity confinement를 추가하는 대신, Runge-Kutta 2차/4차 적분을 사용하고 Bilinear 대신 삼각형 형태의 고차원 보간법을 사용하라고 조언했다. 성능 예산이 허락한다면 확실히 시각적 퀄리티를 끌어올릴 수 있는 훌륭한 접근이다.
- **보존 법칙의 한계:** 수치적 근사(Gauss-Seidel 20회 반복)로 인해 완벽한 질량 보존은 이루어지지 않는다. 하지만 게임 엔진에서는 약간의 질량 손실은 퍼포먼스와 맞바꿀 수 있는 아주 훌륭한 트레이드오프다.

## 나의 결론: 프로덕션 레벨인가?

이 코드를 그대로 실무 프로덕션에 박아 넣을 수 있을까? **절대 아니다.**

모든 계산이 CPU에서 단일 스레드로 돌고 있으며, 루프마다 배열을 순회하고 있다. 모바일 기기나 복잡한 씬에서는 즉각적인 병목을 유발할 것이다. 실무 환경이라면 이 로직을 그대로 GPU로 가져가 Compute Shader로 포팅해야 한다. 텍스처를 그리드로 삼아 핑퐁 렌더링(Ping-pong rendering)을 돌리면 성능을 수십 배 끌어올릴 수 있다.

하지만 이 아티클의 가치는 성능 최적화에 있지 않다. 수식으로 가득 찬 난해한 논문을 누구나 실행해 볼 수 있는 Godot 스크립트로 번역해 냈다는 점, 그리고 각 변수가 물리적으로 어떤 의미를 가지는지 직관적으로 풀어냈다는 점에서 **최고의 레퍼런스** 라 부르기에 손색이 없다.

만약 게임 내에 동적인 안개, 마법 이펙트, 혹은 2D 기반의 상호작용 가능한 물 웅덩이를 구현해야 한다면, 당장 이 저장소를 클론해서 파라미터를 조작해 보길 권한다. 유체의 흐름을 직접 통제하는 것만큼 엔지니어의 도파민을 분비시키는 일도 흔치 않으니까.
