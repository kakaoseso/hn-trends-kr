최근 AI 씬을 보면 모델의 파라미터 크기를 키우는 '체급 키우기' 경쟁과, 이를 어떻게든 엣지 디바이스에 쑤셔 넣으려는 '다이어트' 경쟁이 동시에 벌어지고 있습니다. 15년 넘게 엔지니어링을 해오면서 느끼는 점은, 결국 기술의 대중화는 후자에서 판가름 난다는 것입니다.

클라우드 API에 의존하는 아키텍처는 분명한 한계가 있습니다. Network Latency, 그리고 무엇보다 API 호출마다 발생하는 과금 모델은 개발자와 사용자 모두에게 부담입니다. 특히 이미지 생성처럼 사용자가 프롬프트를 계속 수정하며 반복적인 이터레이션을 거쳐야 하는 작업에서는 클라우드 왕복 비용이 UX를 심각하게 저해합니다.

이런 맥락에서 최근 PrismML에서 발표한 **Bonsai Image 4B** 는 아키텍처 관점에서 굉장히 흥미로운 접근을 보여줍니다. 파라미터 4B(40억 개) 수준의 이미지 생성 모델을 iPhone 17 Pro Max나 Mac M4 Pro 같은 로컬 하드웨어에서 돌리기 위해 1-bit 및 Ternary 양자화(Quantization)를 적용했기 때문입니다.

![](https://cdn.prod.website-files.com/699604cc2b9dd89bdbda0608/6a15cec375689f915406cc3c_grid.png)

### 어떻게 7.75GB 트랜스포머를 0.93GB로 줄였을까?

로컬 환경에서 이미지 생성 모델을 돌릴 때 가장 큰 병목은 컴퓨팅 파워(FLOPS)가 아니라 **Memory Bandwidth** 입니다. 디노이징 스텝마다 거대한 트랜스포머 모델이 메모리에서 연산기로 올라가야 하는데, 대역폭이 좁으면 여기서 엄청난 지연이 발생합니다.

Bonsai Image 4B는 베이스 모델로 FLUX.2 Klein 4B를 사용했습니다. 아키텍처 자체는 그대로 유지하되, 트랜스포머 가중치의 표현 방식을 극단적으로 바꿨습니다.

- **1-bit Variant:** 가중치를 {-1, +1}의 이진 형태로 변환하고, 여기에 FP16 그룹 단위 스케일링 팩터를 적용했습니다. 유효 비트 수는 가중치당 1.125비트입니다. 메모리 압박이 극심한 환경에 적합합니다.
- **Ternary Variant:** 가중치를 {-1, 0, +1}의 3진법으로 표현합니다. 유효 비트 수는 1.71비트입니다. '0'이라는 상태가 추가됨으로써 모델의 표현력이 크게 상승하여 프롬프트 충실도와 시각적 품질이 개선됩니다.

![](https://cdn.prod.website-files.com/699604cc2b9dd89bdbda0608/6a15cd893a2c1d8354bece23_ef1081ac.png)

결과적으로 원본 FLUX.2 Klein 4B의 트랜스포머 크기가 7.75GB였던 반면, 1-bit 모델은 0.93GB(8.3배 감소), Ternary 모델은 1.21GB(6.4배 감소)로 줄어듭니다. 텍스트 인코더와 FP16 VAE를 모두 포함한 전체 페이로드 역시 15.97GB에서 3.42GB ~ 3.88GB 수준으로 떨어집니다.

이 정도면 Apple Silicon의 통합 메모리 구조에서 캐시 히트율을 극대화하고 메모리 I/O를 최소화할 수 있는 완벽한 사이즈입니다. 실제로 Mac M4 Pro에서 512x512 이미지를 생성하는 데 약 6초가 걸린다고 하니, 로컬 개발 환경이나 인앱 탑재용으로 충분히 고려해 볼 만한 수치입니다.

### 해커뉴스 커뮤니티의 반응과 나의 생각

이번 발표에 대해 Hacker News에서도 꽤 열띤 토론이 벌어졌습니다. 몇 가지 흥미로운 포인트와 제 개인적인 견해를 덧붙여 보겠습니다.

**1. 1-bit 이미지 생성기로의 오해**
한 유저는 제목의 '1-bit'를 보고 가중치가 아니라 예전 매킨토시 시절의 1-bit 디더링(Dithering) 흑백 이미지를 생성하는 모델인 줄 알았다는 재미있는 코멘트를 남겼습니다. 사실 엔지니어가 아닌 일반 유저 입장에서는 모델 웨이트의 비트 수라는 개념 자체가 생소할 수 있습니다. 하지만 이는 역설적으로 우리가 얼마나 극단적인 최적화의 시대에 살고 있는지를 보여줍니다.

**2. 클라우드 구독 vs 로컬 하드웨어 투자**
가장 치열했던 논쟁 중 하나는 경제성에 관한 것이었습니다. 한쪽에서는 "API 구독료를 내느니 로컬 하드웨어를 업그레이드해서 평생 무료로 AI를 돌리겠다"고 환호했고, 다른 쪽에서는 "데이터센터의 하드웨어 활용률과 네트워크 인프라를 개인이 이길 수 없다"고 반박했습니다.

제 생각은 이렇습니다. 현재의 클라우드 AI API 가격은 벤처캐피탈(VC) 자본에 의해 심하게 보조금을 받고 있는 비정상적인 상태입니다. 언젠가 인퍼런스 제공자들이 철저한 종량제 기반의 정상적인 마진을 추구하게 되면, API 비용은 지금보다 훨씬 부담스러워질 것입니다. 특히 HN의 한 유저가 언급한 '소셜 개미집(Social Ant Farm)'처럼 24시간 내내 백그라운드에서 에이전트들이 서로 대화하고 상황을 모니터링하는 시스템을 구축한다면, 로컬 인퍼런스는 선택이 아닌 필수가 됩니다.

**3. 진짜 병목은 메모리인가, 속도인가?**
어떤 유저는 "이미지 생성의 진짜 병목은 메모리가 아니라 생성 시간이다. 이미 Draw Things 같은 앱으로 아이폰에서 FLUX.2를 돌릴 수 있다"며 이번 압축의 실효성에 의문을 제기했습니다.

반은 맞고 반은 틀린 이야기입니다. 엣지 디바이스에서 생성 시간(Latency)을 결정짓는 가장 큰 요인이 바로 메모리 대역폭이기 때문입니다. 모델이 VRAM이나 통합 메모리에 한 번에 올라가지 못해 스왑이 발생하거나, 연산기(ALU)가 메모리에서 데이터를 퍼오느라 쉬고 있는 상황(Memory-bound)을 해결하려면 결국 모델의 물리적 크기를 줄여야 합니다. Bonsai Image 4B가 달성한 메모리 풋프린트 감소는 곧바로 처리량(Throughput) 향상과 전력 소모 감소로 이어집니다.

![](https://cdn.prod.website-files.com/699604cc2b9dd89bdbda0608/6a15cc983b75e88cb7a12fac_comparison_grid_horizontal_v3%20(1).png)

### 총평: 프로덕션 레벨인가, 장난감인가?

벤치마크(GenEval, HPSv3) 결과를 보면 Ternary 모델의 경우 원본 FLUX.2의 95% 수준의 정확도를 유지한다고 합니다. 하지만 실무에서 하이엔드 상업용 아트를 생성해야 하는 디자이너에게 이 모델을 쥐여준다면 아마 만족하지 못할 것입니다. 아직 프론티어 모델조차 완벽하지 않은 상황에서 양자화로 인한 디테일 손실은 분명 존재하기 때문입니다.

하지만 이 기술의 진짜 가치는 **Pareto Frontier의 이동** 에 있습니다. 과거에는 1GB 남짓한 메모리로 형편없는 품질의 이미지밖에 만들지 못했다면, 이제는 그 제약 속에서도 모던 디퓨전 트랜스포머의 추론 능력을 온전히 활용할 수 있게 되었습니다.

사용자의 프라이버시가 보장되어야 하는 온디바이스 앱, 네트워크가 불안정한 환경에서의 작업, 혹은 백그라운드에서 끊임없이 시각적 컨텍스트를 생성해야 하는 AI 에이전트 시스템을 설계하고 있다면 Bonsai Image 4B는 훌륭한 선택지가 될 것입니다. Apache 2.0 라이선스로 가중치까지 공개되었으니, 주말에 시간 내서 로컬 장비에 올려 테스트해 보시길 권합니다.
