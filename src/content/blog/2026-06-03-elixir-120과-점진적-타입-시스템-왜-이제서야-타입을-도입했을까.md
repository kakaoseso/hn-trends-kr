## 동적 타입 언어들의 숙명, 그리고 Elixir의 선택

15년 넘게 엔지니어로 구르다 보면 패턴이 보입니다. 처음엔 "개발 속도"와 "유연성"을 외치며 동적 타입 언어를 도입하죠. Python, JavaScript, Ruby가 그랬습니다. 하지만 코드베이스가 커지고 트래픽이 몰리기 시작하면 어김없이 타입을 찾게 됩니다. TypeScript가 세상을 집어삼킨 이유이기도 하죠.

이번에 릴리즈된 Elixir v1.20 소식을 듣고 든 첫 생각은 결국 BEAM 생태계도 이 흐름을 피할 수 없구나 였습니다. Hacker News에서도 누군가 꼬집었듯, 과거 Elixir 커뮤니티 일각에서는 우리에게는 OTP의 마법 같은 장애 복구(Fault Tolerance)가 있으니 정적 타입은 필수가 아니다 라고 방어하기도 했으니까요. 하지만 런타임에 프로세스를 재시작하는 것보다, 컴파일 타임에 버그를 잡는 것이 언제나 더 싸고 안전합니다.

## Elixir의 점진적 타입: TypeScript의 any와는 다르다

이번 v1.20 업데이트의 핵심은 **타입 어노테이션 없이** 코드를 분석해 데드 코드와 런타임에 반드시 실패할 버그를 찾아낸다는 점입니다. 여기서 Elixir 팀이 선택한 접근 방식이 상당히 흥미롭습니다.

보통 점진적 타입 시스템을 도입할 때 가장 골치 아픈 문제는 False Positive(오탐)입니다. 기존의 유연한 코드를 타입 체커가 에러로 뱉어내면 개발자 경험은 나락으로 떨어집니다. 이를 피하기 위해 TypeScript는 any라는 치트키를 제공하죠. 하지만 Elixir의 dynamic() 타입은 결이 다릅니다.

```elixir
def percentage_or_error(value) when is_integer(value) do
  value_or_error =
    if value > 1 do
      value
    else
      "not well"
    end

  if value > 1 do
    value_or_error / 100
  else
    String.upcase(value_or_error)
  end
end
```

위 코드에서 value_or_error는 런타임에 integer() 또는 binary()가 됩니다. 전통적인 정적 타입 시스템이라면 / 연산자나 String.upcase 호출부에서 에러를 뱉을 겁니다. 전달될 수 있는 타입 중 하나가 함수의 시그니처와 맞지 않기 때문이죠.

하지만 Elixir는 이 변수에 dynamic(integer() or binary())라는 타입을 부여합니다. 그리고 **허용되는 타입과 제공된 타입이 완전히 교집합이 없을 때** 만 에러를 발생시킵니다. / 연산자는 숫자를 기대하지만, dynamic 내부에 integer()가 존재하므로 이 코드는 통과됩니다. 반면 아래와 같이 코드를 짜면 어떻게 될까요?

```elixir
Map.fetch!(value_or_error, :some_key)
```

Map.fetch!는 Map 구조를 기대하는데, 변수는 Integer나 Binary만 가질 수 있습니다. 두 타입 간의 교집합이 전혀 없으므로, 컴파일러는 이를 확인된 버그로 간주하고 가차 없이 에러를 뱉어냅니다. 이 방식은 기존 코드베이스를 수정하지 않으면서도 진짜 버그만 족집게처럼 찾아내는 매우 우아한 엔지니어링적 타협점입니다.

## 런타임 오버헤드가 없는 점진적 타입 (Strong Arrows)

개인적으로 이번 업데이트에서 가장 높게 평가하는 부분은 **성능의 보존** 입니다. HN 댓글란에서도 한 유저가 예리하게 지적했듯, Racket이나 Python 같은 언어에서 점진적 타입을 도입할 때 타입 경계를 넘나들면서 발생하는 런타임 캐스팅과 검사 때문에 성능이 박살 나는 경우가 허다합니다.

하지만 Elixir 팀은 Strong Arrows라는 연구 결과를 바탕으로 런타임 체크 없이 Soundness(건전성)를 달성했습니다. 즉, 컴파일러가 뱉어내는 바이트코드는 타입이 없는 기존 코드와 의미론적으로 완벽히 동일하며, 런타임 오버헤드가 **없다** 는 뜻입니다. 이는 Dialyzer의 Success Typing이 주던 모호함과 느린 속도에 지쳐있던 시니어 엔지니어들에게 엄청난 희소식입니다.

## 커뮤니티의 반응과 BEAM의 진입 장벽

HN 스레드를 보면 여전히 Elixir와 BEAM 생태계의 진입 장벽에 대한 토로가 많습니다. 함수형 프로그래밍에 뇌가 적응하지 못하겠다 거나, 프로세스를 수십만 개 띄우라는데 고스트 프로세스나 재시작 전략(Restart Strategy)을 어떻게 짜야 할지 막막하다는 의견들이죠.

솔직히 말해, 저도 처음 Erlang과 Elixir를 접했을 때 똑같은 벽을 느꼈습니다. 객체 지향의 상태 관리에 익숙한 뇌를 데이터 변환과 파이프라인 중심으로 재배선하는 과정은 고통스럽습니다. 게다가 OTP 디자인 패턴은 웹 프레임워크 튜토리얼 몇 개 따라 한다고 체득되는 것이 아닙니다.

하지만 이 생태계가 주는 강력함은 분명합니다. 단일 노드에서 수백만 개의 웹소켓을 가볍게 처리하고, 시스템 일부가 뻗어도 전체 시스템이 무너지지 않는 아키텍처를 언어 레벨에서 지원합니다. 여기에 강력한 타입 시스템까지 얹어진다면? Elixir는 더 이상 일부 매니아들의 장난감이 아니라, 고성능 분산 시스템을 구축하기 위한 가장 실용적인 선택지로 자리 잡을 것입니다.

## 결론 (Verdict)

이번 v1.20 릴리즈는 완벽한 정적 타입 언어로의 전환을 의미하지는 않습니다. 아직 사용자가 직접 타입 시그니처를 정의할 수 없고, 재귀 타입이나 파라메트릭 타입 같은 과제들이 남아있기 때문입니다.

- **도입해야 할까?:** 무조건 업데이트하십시오. 코드 수정 없이 공짜로 버그를 찾아주고 데드 코드를 정리해 줍니다.
- **미래 전망:** Elixir 팀의 행보는 매우 신중하고 학구적입니다. 수학적으로 증명된 타입 시스템을 차근차근 언어에 녹여내고 있습니다.

기존의 유연함을 해치지 않으면서도 타입 안정성을 확보하려는 Elixir의 이번 시도는, 동적 타입 언어가 진화해야 할 가장 이상적인 방향성을 보여주고 있습니다. 앞으로 이어질 릴리즈에서의 타입 시그니처 도입이 벌써부터 기다려집니다.
