시니어 엔지니어로 일하다 보면 언어의 화려한 문법보다는 빌드 시스템의 속도, 링커의 효율성, 그리고 OS 레벨의 시스템 콜을 얼마나 투명하게 다룰 수 있는지에 더 집착하게 됩니다. 최근 공개된 Zig 0.16.0 및 다가오는 0.17.0 릴리스 노트를 읽으면서, 오랜만에 진짜 '시스템 프로그래밍' 언어가 가져야 할 집요함을 엿볼 수 있었습니다.

단순히 "C를 대체하겠다"는 마케팅 용어가 아니라, 컴파일러와 링커를 밑바닥부터 뜯어고치며 엔지니어링의 본질적인 문제를 해결해 나가는 과정이 매우 인상적입니다. 오늘은 이번 Zig 개발 일지에서 제 눈길을 사로잡은 몇 가지 핵심 기술적 성취와, 이것이 실제 프로덕션 환경에 시사하는 바를 파헤쳐보겠습니다.

## 100ms의 마법: 자체 ELF 링커와 증분 컴파일

C++ 생태계에서 우리는 빌드 시간을 단축하기 위해 LTO를 끄거나, Gold나 Mold 같은 외부 링커를 도입하며 수많은 시간을 허비해왔습니다. Zig는 아예 자체 ELF 링커를 만들어 이 문제를 정면 돌파하고 있습니다.

이번 업데이트의 핵심은 x86_64 Linux 환경에서 외부 라이브러리(libc, LLVM 등)를 링크하면서도 성능 오버헤드 없이 빠른 증분 빌드(Incremental Rebuild)를 지원한다는 점입니다.

```bash
zig build -Dno-lib -Denable-llvm -fincremental --watch
...
└─ compile exe zig Debug native success 244ms
└─ compile exe zig Debug native success 228ms
```

솔직히 처음엔 그저 '장난감 프로젝트용이겠지'라고 생각했습니다. 하지만 Zig 컴파일러 자체(LLVM과 LLD를 포함하는 거대한 코드베이스)를 이 링커로 빌드해냈다는 것은 엄청난 마일스톤입니다. Hacker News의 한 유저가 지적했듯, 서브 100ms 단위의 빌드 타임은 단순히 '시간을 아껴주는' 것을 넘어 개발자의 사고방식 자체를 바꿉니다. 코드 수정 후 결과를 확인하기까지의 Latency가 줄어들면, 더 많은 실험을 주저 없이 할 수 있게 되기 때문입니다.

## Kernel32.dll 우회: 진짜 시스템 엔지니어링이란 이런 것

이번 릴리스 노트에서 가장 제 가슴을 뛰게 한 부분입니다. Windows 환경에서 개발해 본 엔지니어라면 Kernel32.dll이 얼마나 많은 불필요한 추상화와 숨겨진 상태를 가지고 있는지 아실 겁니다.

Andrew Kelley는 여기서 타협하지 않고, Kernel32.dll을 건너뛰어 ntdll.dll을 직접 호출하는 방식을 택했습니다. 예를 들어 표준 파일 읽기 함수를 볼까요?

```zig
pub extern "ntdll" fn NtReadFile(
    FileHandle: HANDLE,
    Event: ?HANDLE,
    ApcRoutine: ?*const IO_APC_ROUTINE,
    ...
) callconv(.winapi) NTSTATUS;
```

기존의 ReadFile은 내부적으로 불필요한 힙 할당을 발생시키고, 에러 코드를 숨긴 채 BOOL을 반환하여 GetLastError를 강제합니다. 반면 NtReadFile은 NTSTATUS를 직접 반환하며, 비동기 I/O 처리 시 무거운 Event 객체 대신 APC(Asynchronous Procedure Call) 루틴을 사용하여 리소스 낭비를 원천 차단합니다.

과거 Windows 환경에서 원인을 알 수 없는 메모리 스파이크나 핸들 누수 문제로 며칠을 밤새워 디버깅했던 기억이 납니다. 대부분 OS가 제공하는 불투명한 Wrapper 라이브러리 때문이었죠. Zig처럼 OS의 저수준 인터페이스를 직접 타격하는 접근 방식은, 극단적인 성능과 예측 가능성이 필요한 시스템에서 엄청난 무기가 될 것입니다.

## 빌드 시스템 구조 개편: Configurer와 Maker의 분리

빌드 스크립트(build.zig)가 실행될 때마다 전체 빌드 시스템이 함께 컴파일되던 기존의 비효율을 걷어냈습니다. 이제는 빌드 로직이 메모리에 그래프를 구성하면 이를 직렬화하여 캐싱하고, 실제 실행을 담당하는 프로세스(Maker)는 릴리스 모드로 한 번만 컴파일되어 이 캐시를 재사용합니다.

그 결과 zig build -h 명령어의 실행 시간이 150ms에서 14ms로 90% 이상 단축되었습니다. build.zig 파일이 변경되지 않았다면 불필요한 재평가를 완벽히 스킵하는 이 구조는, 프로젝트 규모가 커질수록 그 진가를 발휘할 것입니다.

## io_uring과 완벽한 I/O 추상화

Go 언어는 훌륭하지만 런타임과 GC의 늪에서 벗어날 수 없고, Rust는 Tokio 같은 비동기 런타임이 코드베이스 전체를 감염시키는 단점이 있습니다.

Zig는 std.Io 인터페이스를 통해 이 문제를 우아하게 해결하려 합니다. 어플리케이션 코드는 완전히 동일하게 유지한 채, 진입점(Main)에서 I/O 구현체를 std.Io.Threaded에서 std.Io.Evented(io_uring 기반)로 갈아끼우기만 하면 됩니다. 유저스페이스 스택 스위칭(Fiber)을 활용하여 동기 코드처럼 작성하지만 비동기로 동작하게 만드는 이 접근법은, 아직 실험적이지만 제가 꿈꾸던 완벽한 백엔드 프로그래밍 모델에 가장 근접해 있습니다.

## 생태계의 반응: C의 진정한 후계자

Hacker News 스레드에서 가장 흥미로웠던 논쟁은 역시 "Zig vs Rust vs Go"였습니다. 많은 개발자들이 "Rust가 새로운 C++라면, Zig는 새로운 C"라는 데 동의하고 있습니다.

물론 @cImport 기능이 제거되고 명시적인 설정으로 바뀐 것에 대해 불만을 토로하는 유저도 있었습니다. 기존 C 프로젝트를 점진적으로 포팅하던 입장에선 꽤 뼈아픈 변화일 수 있습니다. 하지만 언어의 명확성과 빌드 시스템의 일관성을 위해 매직(Magic)을 제거하는 것은 장기적으로 올바른 결정이라고 생각합니다.

Rust의 엄격한 소유권 모델이 주는 피로감에 지친 엔지니어들에게, Zig는 수동 메모리 관리의 통제권을 돌려주면서도 C보다 훨씬 안전하고 쾌적한 도구를 제공하고 있습니다.

## 총평: 프로덕션 도입, 준비되었는가?

아직 1.0이 나오지 않았다는 점(현재 0.17.0을 향해 가는 중)을 고려하면, 미션 크리티컬한 금융 시스템이나 대규모 엔터프라이즈 백엔드에 당장 Zig를 도입하라고 권하지는 않겠습니다.

하지만 C/C++로 작성해야만 했던 고성능 CLI 툴, 임베디드 시스템, 오디오 엔진, 혹은 JNI/FFI용 코어 모듈을 새로 시작한다면? 저는 주저 없이 Zig를 선택할 것입니다. 100ms 단위의 피드백 루프와 OS 밑바닥을 투명하게 제어할 수 있는 이 강력한 도구는, 시스템 엔지니어링의 즐거움을 다시 일깨워주기에 충분합니다.
