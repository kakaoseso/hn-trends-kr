최근 Hacker News를 보면 하루가 멀다 하고 새로운 프로그래밍 언어와 프레임워크들이 올라옵니다. 대부분은 흥미로운 시도이거나 특정 Pain point를 해결하기 위한 엔지니어들의 치열한 고민이 담겨 있죠. 하지만 가끔은... 제 15년 이상의 엔지니어링 경력과 상식을 완전히 뒤흔드는, 아니 정확히 말하면 '어리둥절하게 만드는' 기괴한 프로젝트를 마주하게 됩니다.

오늘 이야기할 **Yon** 이라는 언어가 정확히 그런 케이스입니다. 

이 언어의 공식 문서를 처음 열었을 때, 저는 제가 모르는 새로운 패러다임이 탄생한 줄 알았습니다. 하지만 문서를 파고들고, 코드를 뜯어보고, Hacker News의 반응을 살펴보면서 이것이 현대 소프트웨어 엔지니어링이 직면한 아주 기괴하고 새로운 문제라는 것을 깨달았습니다.

### 화려한 버즈워드의 향연: Yon의 첫인상

Yon의 소개 페이지는 그야말로 논문에서나 볼 법한 수학적, 철학적 용어들의 뷔페입니다.

- **Topos-oriented programming:** 카테고리 이론의 토포스(Topos)를 프로그래밍 패러다임으로 가져왔다고 합니다.
- **Content-addressed lattice heap:** 메모리 할당을 Leech lattice(Λ24) 기하학을 사용해 처리합니다.
- **No GC, No Threads, No Exceptions:** 가비지 컬렉터도, 스레드도, 예외 처리도 없습니다.

코드는 대략 이렇게 생겼습니다.

```yon
fun main(): number {
  be greeting holds "ciao, mondo"
  // interned on the heap
  be _ holds String.print(greeting)
  return 0
}
```

문법 자체는 약간의 Kotlin이나 TypeScript 냄새가 나지만, `be`나 `holds` 같은 독특한 키워드를 사용합니다. 여기까지만 보면 "오, 뭔가 극단적인 Immutable 아키텍처와 수학적 증명을 결합한 실험적인 언어인가?" 싶습니다.

하지만 시스템 설계자로서 조금만 더 깊이 들어가 보면, 이 모든 것이 정교하게 쌓아 올린 모래성이라는 것을 알 수 있습니다.

### 메모리 모델의 모순: 196,560개의 슬롯?

제가 가장 경악했던 부분은 메모리 모델, 즉 Heap 구조입니다. 

Yon은 Leech lattice를 이용해 힙당 정확히 **196,560개의 슬롯** 만 존재한다고 주장합니다. 값을 해싱해서 동일한 컨텐츠면 기존 슬롯을 반환하기 때문에, 아무리 큰 데이터라도 구조적 동등성(structural equality) 비교가 O(1)에 끝난다는 논리입니다.

솔직히 말해서, 이건 일반적인 범용 프로그래밍 언어의 힙 설계로서는 완전히 넌센스입니다. 

만약 이 언어로 웹 서버를 띄워서 유저 리퀘스트를 처리한다고 가정해 봅시다. 매 요청마다 고유한 문자열이나 페이로드가 생성될 텐데, GC도 없는 상태에서 196,560개의 슬롯이 꽉 차면 어떻게 될까요? 해시 충돌은 수학적 기하학이라는 단어로 마법처럼 해결되지 않습니다. 메모리가 무한히 늘어나거나, 아니면 프로그램이 그대로 패닉 상태에 빠지겠죠.

실제로 HN의 한 유저가 "유니크한 컨텐츠가 쏟아지는 웹 서버 같은 건 어떻게 처리하냐"고 묻자, "각 요청마다 서브 프로세스를 띄우고 끝나면 종료(exit)해라"라는 식의 답변이 돌아왔습니다. CGI 시절로의 회귀인가요? Latency와 Throughput을 조금이라도 고민해 본 엔지니어라면 절대 할 수 없는 발상입니다.

### PL 이론의 파괴: 흉내만 낸 타입 시스템

Yon은 Homotopy Type Theory(HoTT)와 Dependent Type을 차용했다고 문서에 적어두었습니다. 하지만 소스코드를 뜯어본 PL(Programming Language) 전공자들의 분석은 참담했습니다.

- **Dependent Type의 부재:** 문서와 달리 실제 AST(Abstract Syntax Tree)를 보면 타입이 Term에 의존하지 않는 단순 타입(Simply-typed) 시스템에 불과합니다.
- **Normalization 실패:** 직관주의 논리(Intuitionistic logic)를 표방한다면서 Classical boolean을 섞어 씁니다. 이는 증명 불감증(proof irrelevance)과 맞물려 타입 시스템의 Normalization을 완전히 박살 냅니다.

카테고리 이론 박사 학위(PhD)를 가진 한 유저조차 "Leech lattice가 메모리 저장에 무슨 가치가 있는지 전혀 모르겠다"고 코멘트를 남겼습니다. 수학적 개념과 프로그래밍 언어의 설계가 전혀 맞물리지 않고 겉돌고 있는 것입니다.

### AI Psychosis (AI 정신증) 시대의 도래

HN 스레드에서 가장 제 뼈를 때렸던 코멘트는 바로 이것이었습니다. 

> "이건 마치 누군가 AI 환각(AI psychosis)에 빠져서, 자기가 Gemini와 함께 어떤 물리학적/형이상학적 돌파구를 찾아냈다고 착각하는 것과 같다."

과거에는 언어를 디자인하려면 컴파일러 이론, 메모리 관리, 타입 시스템에 대한 깊은 이해가 필수적이었습니다. 하지만 이제는 LLM을 사용해 그럴듯한(plausible) 영문 문서와 보일러플레이트 코드를 순식간에 찍어낼 수 있습니다. 

문제는 LLM이 '단어들의 통계적 연관성'은 기가 막히게 조합하지만, 그 기저에 깔린 **엔지니어링 철학과 수학적 정합성** 은 이해하지 못한다는 점입니다. Topos, Lattice, Dependent Type 같은 멋진 단어들을 프롬프트에 때려 넣고 "이걸 기반으로 혁신적인 언어 문서를 작성해 줘"라고 하면 딱 Yon 같은 결과물이 나옵니다.

이런 '그럴듯한 쓰레기(Plausible Slop)'는 오픈소스 생태계에 큰 위협이 됩니다. 진짜 가치 있는 아이디어와 AI가 생성한 환각을 구분하기 위해 시니어 엔지니어들의 귀중한 리뷰 리소스가 낭비되기 때문입니다.

### 결론: 우리는 무엇을 배워야 하는가

Yon은 프로덕션 레벨은커녕, 진지한 학술적 토이 프로젝트로 보기도 어렵습니다. (개인적으로는 정교한 어그로이거나, AI에 심취한 누군가의 안타까운 결과물이라고 생각합니다.)

하지만 이 해프닝은 우리에게 매우 중요한 교훈을 줍니다. 

기술을 평가할 때 화려한 버즈워드에 압도되지 마십시오. 어떤 기술이 "우리는 X라는 쩌는 수학적 개념을 써서 Y를 해결했다"고 주장한다면, 반드시 **"그래서 극단적인 엣지 케이스(Edge case)에서 메모리와 CPU는 물리적으로 어떻게 동작하는가?"** 를 물어야 합니다. 

앞으로 시니어 엔지니어와 아키텍트의 가장 중요한 역량은 코드를 빠르게 짜는 것이 아닐 겁니다. AI가 무한대로 생성해 내는 '그럴듯해 보이는 아키텍처'의 논리적 허점을 빠르게 짚어내고, 시스템의 물리적 한계를 검증하는 **필터링(Filtering) 능력** 이 핵심이 될 것입니다.
