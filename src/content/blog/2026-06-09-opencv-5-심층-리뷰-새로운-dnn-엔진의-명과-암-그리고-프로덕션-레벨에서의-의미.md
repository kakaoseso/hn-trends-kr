제가 처음 컴퓨터 비전 업계에 발을 들였던 15년 전, CUDA 지원을 활성화해서 OpenCV를 소스코드부터 빌드하는 것은 일종의 통과의례였습니다. 그 이후로 꽤 오랜 시간이 흘렀지만, 여전히 영상이나 이미지를 픽셀 단위로 읽어 들일 때 `cv2.imread`만큼 만만한 녀석은 없습니다. 

최근 OpenCV 5가 발표되었습니다. 재단 측에서는 "컴퓨터 비전 역사상 가장 큰 도약"이라고 포장하고 있죠. 하지만 Hacker News의 시니어 엔지니어들은 발표 글이 전형적인 'AI 생성형 마케팅 문구'라며 차가운 반응을 보이고 있습니다. 저 역시 PR용 미사여구에는 관심이 없습니다. 우리가 진짜 알아야 할 것은 "그래서 프로덕션 환경에서 쓸 만한가?" 그리고 "내 아키텍처를 어떻게 바꿀 것인가?" 입니다.

오늘은 마케팅 거품을 걷어내고, 시니어 엔지니어의 관점에서 OpenCV 5의 진짜 변화를 뜯어보겠습니다.

![Opencv 5](https://opencv.org/wp-content/uploads/2026/06/opencv-5.png)

## 레이어에서 그래프로: 완전히 뜯어고친 DNN 엔진

과거 OpenCV 4.x 시절의 DNN 모듈을 프로덕션에서 써보신 분들은 아실 겁니다. 새로운 모델을 ONNX로 익스포트하고 OpenCV에서 불러올 때마다 일종의 기도 메타가 필요했죠. 지원하지 않는 오퍼레이터 에러가 밥 먹듯이 튀어나왔으니까요. 기존 4.x 엔진의 ONNX 커버리지는 약 22%에 불과했습니다.

OpenCV 5는 이 커버리지를 80% 이상으로 끌어올렸습니다. 비결은 단순한 오퍼레이터 추가가 아니라, 엔진의 근본적인 구조 변경에 있습니다. 기존 엔진이 네트워크를 평면적인 레이어의 나열로 보고 하나씩 순회했다면, 5.x의 엔진은 모델을 **타입이 지정된 연산 그래프 (Typed Operation Graph)** 로 이해합니다.

![Graph Engine](https://opencv.org/wp-content/uploads/2026/06/image.jpeg)

이러한 그래프 기반 접근은 최신 딥러닝 컴파일러들이 쓰는 방식과 동일합니다. 덕분에 다음과 같은 최적화가 가능해졌습니다.

- **Dynamic Shapes:** 더 이상 입력 텐서의 크기를 미리 고정할 필요가 없습니다.
- **Operator Fusion:** MatMul -> Softmax -> MatMul 패턴을 발견하면 이를 단일 FlashAttention 연산으로 퓨전(Fusion)해버립니다. 메모리 I/O를 줄여 Latency를 극단적으로 낮출 수 있죠.

### 하지만... CPU 전용이라고?

벤치마크를 보면 OpenCV 5의 새로운 엔진은 CPU 환경에서 ONNX Runtime보다 빠릅니다. YOLOv8n 같은 모델에서 약 11% 더 낮은 Latency를 보여주죠. 

하지만 HN에서도 강하게 지적된 부분이 있습니다. 이 새롭고 멋진 그래프 엔진이 현재 **CPU 전용** 이라는 점입니다. 

솔직히 말씀드리면, 2026년에 메이저 CV 라이브러리의 헤드라인 기능이 CPU 전용 추론 엔진이라는 점은 다소 아쉽습니다. 프로덕션 환경에서 Throughput과 Latency가 중요한 실시간 영상 처리 파이프라인을 구축할 때, 우리는 보통 TensorRT나 최소한 GPU 백엔드를 씁니다. 

다행히 하위 호환성을 위해 단일 API 뒤에 세 가지 엔진을 숨겨두었습니다. 

```python
import cv2 as cv

# ENGINE_AUTO (기본값): 새 엔진을 먼저 시도하고, 실패하면 클래식 엔진으로 폴백
net = cv.dnn.readNetFromONNX("model.onnx")

# CUDA나 OpenVINO 같은 비-CPU 백엔드를 쓰려면 클래식 엔진을 명시해야 할 수도 있습니다.
net_classic = cv.dnn.readNetFromONNX("model.onnx", engine=cv.dnn.ENGINE_CLASSIC)
```

당장 GPU 가속이 필요하다면 기존처럼 `ENGINE_CLASSIC`이나 빌드 시 추가할 수 있는 `ENGINE_ORT` (ONNX Runtime 래퍼)를 사용해야 합니다. 향후 5.x 마이너 업데이트에서 네이티브 GPU 지원이 추가된다고 하니 이 부분은 지켜봐야겠습니다.

## OpenCV에 LLM이 들어온 이유: 피처 크립인가, 신의 한 수인가?

이번 릴리스에서 가장 당혹스러우면서도 흥미로웠던 부분은 OpenCV 내부에 VLM (Vision-Language Model)과 LLM을 구동하기 위한 **네이티브 토크나이저** 와 **KV-Cache** 가 탑재되었다는 점입니다. Qwen 2.5, Gemma 3 같은 모델을 외부 프레임워크 없이 돌릴 수 있습니다.

처음 이 소식을 들었을 때 제 반응은 "왜 영상 처리 라이브러리에 텍스트 생성 기능을 욱여넣지?" 였습니다. 전형적인 소프트웨어 비대화 (Feature Creep)로 보였거든요. HN 커뮤니티의 반응도 비슷했습니다. "그냥 YOLO 쓰면 30M 파라미터로 끝날 객체 인식을 굳이 8B 파라미터짜리 VLM으로 해야 하나?"

하지만 임베디드나 엣지 디바이스에서 OCR 후처리나 제로샷(Zero-shot) 이미지 캡셔닝을 해야 하는 상황을 가정해 봅시다. 이 기능 하나 때문에 무거운 PyTorch나 HuggingFace 생태계를 통째로 컨테이너에 말아 넣는 것은 엄청난 낭비입니다. OpenCV 바이너리 하나로 VLM 파이프라인을 엔드투엔드로 해결할 수 있다면, 엣지 환경에서는 꽤 매력적인 선택지가 될 수 있습니다.

![LaMa](https://opencv.org/wp-content/uploads/2026/06/LaMa.jpg)

개인적으로는 LaMa 모델을 이용한 인페인팅(Inpainting) 기능이 더 실용적으로 다가왔습니다. 마스크 영역을 지정하고 `net.forward()` 한 번만 호출하면 감쪽같이 객체가 지워집니다. 전처리 로직이 내장되어 있어 코드가 극단적으로 짧아집니다.

## 진짜 엔지니어링의 승리: Core와 HAL의 현대화

마케팅 부서에서는 DNN과 AI를 강조하지만, 시니어 엔지니어인 제가 이번 릴리스에서 가장 환호했던 부분은 바로 코어 아키텍처의 개선입니다.

1. **0D / 1D 텐서 지원:** 드디어 `cv::Mat`이 스칼라(0D)와 1D 배열을 네이티브로 지원합니다. 4.x 시절 억지로 차원을 늘리느라 `reshape`를 남발하던 끔찍한 코드들을 걷어낼 수 있게 되었습니다.
2. **FP16 / BF16 데이터 타입:** 최신 AI 워크로드에 맞춰 반정밀도 부동소수점 타입이 1급 시민(First-class citizen)으로 올라왔습니다. 타입 변환 오버헤드가 크게 줄어듭니다.
3. **C API의 완전한 퇴출:** 레거시 C API가 공식적으로 Deprecated 되었습니다. 진작에 했어야 할 일입니다.

더불어 새로운 **HAL (Hardware Acceleration Layer)** 도입은 아키텍처 관점에서 매우 훌륭한 결정입니다. 기존에는 칩셋마다 파편화된 `#ifdef` 떡칠 코드가 존재했습니다. 이제는 단일 HAL 컨트랙트를 통해 Arm KleidiCV (AWS Graviton, Cortex-A), Qualcomm FastCV (Snapdragon DSP/NPU), RISC-V Vector (RVV) 등으로 자동 라우팅됩니다.

내부적으로 Universal Intrinsics 2.0을 사용해 단일 벡터 코드로 다양한 아키텍처의 SIMD 명령어를 타겟팅합니다. 개발자는 하드웨어를 신경 쓰지 않고 코드를 작성해도 디바이스에 맞는 최적의 가속을 무료로 얻게 됩니다.

## Hacker News의 시선과 나의 결론

HN 스레드(https://news.ycombinator.com/item?id=48421858)를 보면 이번 발표에 대한 비판이 꽤 맵습니다. AI로 생성된 듯한 매끄럽기만 한 블로그 포스트와, 엉성한 아키텍처 다이어그램이 엔지니어들의 반감을 샀죠. 또한, TensorRT가 지배하는 상용 프로덕션 환경을 무시하고 ONNXRuntime과의 CPU 벤치마크만 내세운 점도 비판의 도마 위에 올랐습니다.

그들의 비판에 100% 동의합니다. OpenCV 5가 당장 클라우드 환경의 대규모 모델 서빙 인프라를 대체할 일은 없을 것입니다.

하지만 우리가 OpenCV를 쓰는 진짜 이유를 상기해 볼 필요가 있습니다. OpenCV는 언제나 '가장 접근하기 쉽고, 범용적이며, 디펜던시 지옥이 없는' 도구였습니다. 

이번 OpenCV 5는 낡은 배관을 최신 규격으로 교체하는 대공사를 성공적으로 마쳤습니다. 그래프 기반 DNN 엔진, 1D 텐서 지원, 모바일/엣지 친화적인 새로운 HAL은 앞으로 10년간 OpenCV가 살아남기 위한 튼튼한 기반이 될 것입니다. 

**Verdict:** 
당장 기존 파이프라인을 다 엎고 OpenCV 5 DNN으로 갈아탈 필요는 없습니다. 하지만 신규 프로젝트, 특히 리소스가 제한된 엣지 디바이스나 크로스 플랫폼(모바일, 데스크톱, 라즈베리파이 등)을 타겟팅하는 애플리케이션이라면 OpenCV 5는 종속성을 획기적으로 줄여주는 강력한 무기가 될 것입니다. 엔진 폴백(ENGINE_AUTO) 기능 덕분에 업그레이드 리스크도 낮으니, 개발 환경에서 5.x 브랜치를 당겨와 테스트해 보시길 권장합니다.
