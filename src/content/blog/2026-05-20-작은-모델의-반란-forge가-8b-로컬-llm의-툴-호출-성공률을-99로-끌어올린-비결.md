최근 로컬 LLM 씬을 지켜보면 참 재밌습니다. 모델의 가중치(weights)를 깎고 튜닝하는 데 혈안이 되어 있지만, 정작 프로덕션 환경에서 에이전틱(Agentic) 워크플로우를 돌려보면 8B 수준의 작은 모델들은 처참하게 무너집니다. JSON을 뱉으라고 했더니 장황한 소설을 쓰고 있거나, 존재하지도 않는 툴을 호출하다가 루프에 빠져버리죠.

그런데 며칠 전 Hacker News에서 꽤 흥미로운 프로젝트를 발견했습니다. **Forge** 라는 이름의 이 오픈소스는 8B 로컬 모델(Ministral-3 8B 등)의 멀티스텝 툴 호출 성공률을 53%에서 99%까지 끌어올렸다고 주장합니다. 처음엔 '또 그저 그런 프롬프트 엔지니어링 래퍼(wrapper)겠지' 하고 넘기려다 아키텍처를 뜯어봤는데, 생각보다 훨씬 엔지니어링적으로 탄탄하고 실용적인 접근을 취하고 있었습니다.

오늘은 15년 차 엔지니어의 시각에서 Forge가 어떻게 작은 모델의 멱살을 잡고 하드캐리하는지, 그리고 이 과정에서 우리가 배울 수 있는 시스템 설계의 교훈은 무엇인지 딥다이브 해보겠습니다.

## 1. 텍스트 생성을 원천 차단하는 Synthetic 'respond' Tool

제가 Forge의 설계에서 가장 감탄한 부분은 바로 프록시 서버 모드에서 동작하는 방식입니다. 작은 모델들의 가장 큰 문제 중 하나는 '언제 툴을 호출하고, 언제 텍스트로 대답해야 하는지'를 제대로 구분하지 못한다는 점입니다.

Forge는 이 문제를 아주 무식하지만 확실한 방법으로 해결합니다. 모델에게 일반 텍스트 응답을 허용하지 않고, 백그라운드에서 `respond(message="...")`라는 가상의 툴을 주입해버립니다.

- **동작 방식:** 클라이언트(Continue, Aider 등)가 요청을 보내면, Forge 프록시가 이를 가로채서 모델에게 '너는 무조건 툴을 호출해야 해'라고 강제합니다. 모델이 사용자에게 말을 걸고 싶다면 텍스트를 생성하는 게 아니라 `respond` 툴을 호출해야 합니다.
- **결과:** 프록시는 이 `respond` 호출을 가로채서 다시 일반 텍스트(finish_reason: "stop")로 변환해 클라이언트에게 돌려줍니다.

이게 왜 중요할까요? 모델을 항상 '툴 호출 모드(Tool-calling mode)'에 가둬둠으로써, Forge가 제공하는 모든 가드레일(파싱 복구, 재시도 강제 등)이 텍스트 생성 단계에서도 동일하게 적용될 수 있기 때문입니다. 작은 모델에게 선택의 자유를 주지 않고 인터페이스를 강제하는 전형적인 방어적 프로그래밍(Defensive Programming) 패턴입니다.

## 2. '희망 회로'를 끊어내는 Nudge와 가드레일

대부분의 기존 하네스(Opencode 등)도 실패 시 재시도(Retry) 로직을 가지고 있습니다. 툴 호출이 실패하면 에러 메시지를 그대로 모델에게 던져주고 '알아서 고쳐봐'라고 하죠. GPT-4o나 Claude 3.5 Sonnet 같은 프론티어 모델들은 이 에러 로그를 읽고 스스로 문맥을 파악해 수정합니다.

하지만 8B 모델에게 날 것의 에러 스택을 던져주면 패닉에 빠집니다. Forge는 여기서 **Nudge(넛지)** 라는 개념을 도입합니다.

단순히 `Error: Tool X not found`라고 던져주는 대신, 프레임워크 레벨에서 개입하여 `Tool X does not exist, call one of the available tools: A, B, C`라고 구체적인 지시를 내립니다. JSON이 깨졌다면 레스큐 파서(Rescue Parser)가 개입해 복구를 시도하고, 모델이 필수 단계를 건너뛰고 멋대로 종료하려 하면 '이 작업을 완료하려면 먼저 Y 툴을 실행해야 해'라고 강제(Step Enforcement)합니다.

HN의 한 유저가 남긴 댓글이 이 상황을 완벽하게 요약합니다.
> "이건 마치 주니어 개발자에게 무제한의 시간을 주고 목표를 달성할 때까지 계속 다른 걸 시도해보라고 하는 것과 같습니다."

맞습니다. 8B 모델은 훌륭한 타이핑 속도를 가진 주니어입니다. 이들이 엉뚱한 길로 빠지지 않게 옆에서 계속 넛지를 주는 시니어(Forge)가 필요한 것이죠.

## 3. 컨텍스트 압축과 '유효 어텐션(Effective Attention)'의 붕괴

이 프로젝트와 HN 스레드에서 가장 흥미로웠던 논의는 **유효 어텐션(Effective Attention)** 에 대한 것이었습니다.

최신 모델들은 128k 이상의 거대한 컨텍스트 윈도우를 자랑하지만, 에이전틱 워크플로우를 돌려보면 60k~80k 토큰 부근에서 모델이 이전 문맥을 '까먹는' 게 아니라 '대충 읽기(Skim)' 시작합니다. 윈도우 밖으로 밀려난 게 아니라, 어텐션 가중치가 희석되는 현상입니다.

Forge는 이를 방어하기 위해 `TieredCompact`라는 컨텍스트 관리 전략을 사용합니다.

```python
ctx = ContextManager(strategy=TieredCompact(keep_recent=2), budget_tokens=8192)
runner = WorkflowRunner(client=client, context_manager=ctx)
```

오래된 툴 호출 내역에서 '응답(Response)' 부분은 날리거나 요약하고 '호출(Call)' 기록만 남기는 식입니다. 사실 우리가 터미널에서 작업할 때 10번 전의 `grep` 명령어 결과값 전체가 필요한 게 아니라, '내가 아까 그 파일을 검색했었다'는 사실 자체가 중요한 것과 같은 이치입니다.

## 4. 백엔드 서버에 따른 성능의 미스터리

저자가 남긴 코멘트 중 하나는 로컬 LLM을 서빙하는 엔지니어들에게 큰 충격을 주었습니다. 동일한 가중치(Mistral-Nemo 12B)를 사용했음에도 불구하고, 서빙 백엔드에 따라 툴 호출 정확도가 극단적으로 차이 났다는 점입니다.

- llama-server (Native FC): 7%
- Llamafile (Prompt mode): 83%

이건 정말 말도 안 되는 수치입니다. 호스팅 컨테이너의 차이가 모델 자체의 성능 차이를 압도해버린 겁니다. 네이티브 함수 호출 템플릿의 결함인지, 프롬프트 인젝션 방식의 승리인지 명확히 밝혀지진 않았지만, 우리가 로컬 모델을 평가할 때 '어떤 백엔드로 서빙했는가'가 핵심 변수라는 점을 시사합니다. (참고로 저자는 최종적으로 llama-server에 jinja 템플릿을 조합한 세팅을 최고 성능으로 추천했습니다.)

## 결론: 프로덕션에 도입할 만한가?

만약 당신이 GPT-4나 Claude Opus만 사용한다면 Forge는 오버엔지니어링일 수 있습니다. 프론티어 모델들은 이미 스스로 충분히 똑똑하니까요.

하지만 비용, 보안, 혹은 온프레미스 제약 때문에 **로컬 8B~14B 모델로 에이전트 시스템을 구축해야 한다면, Forge와 같은 가드레일 미들웨어는 선택이 아니라 필수** 입니다. 모델의 추론 능력(Reasoning)에 모든 것을 의존하는 시대는 지나가고 있습니다. 이제는 '멍청하지만 빠른 모델'을 시스템 엔지니어링으로 보완하여 '느리지만 확실한 결과'를 만들어내는 아키텍처가 실무에서 훨씬 더 빛을 발할 것입니다.

개인적으로는 ETTWS(Estimated Time To Working Solution)라는 새로운 지표를 도입해 파이프라인을 최적화하겠다는 저자의 철학이 아주 마음에 듭니다. 똑똑한 원숭이 천 마리가 타자기를 두드리게 하려면, 최소한 타자기가 고장 났을 때 종이를 갈아끼워 줄 시스템은 있어야 하지 않겠습니까?
